# Проверка персональной ставки demo-0.3

Правила и контракт: [PRICING.md](PRICING.md). Общие способы запуска и запасная команда Node для этого ноутбука — [FRONTEND_CHECK.md](FRONTEND_CHECK.md). Нужен настоящий API, не dev:mock: автономный макет остается на историческом demo-0.2 и не проверяет персональное ценообразование.

## 1. Обновить локальное окружение

Если старые FastAPI/Vite запущены в ваших терминалах, остановить их Ctrl+C. PostgreSQL и уже работающий Ollama останавливать не нужно. Из корня:

```powershell
cd C:\alpha\alpha-hakaton
.\.venv\Scripts\python.exe -m credit_cabinet.seed --dataset demo_data/demo_0_3 --check-only
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m credit_cabinet.seed --dataset demo_data/demo_0_3
.\.venv\Scripts\python.exe -m alembic current
```

Ожидается актуальная вершина 0006_scenario_sets. Условия ставок добавила предыдущая 0005_personal_pricing; сохранённые варианты описаны в [SCENARIO_SETS_CHECK.md](SCENARIO_SETS_CHECK.md). На ноутбуке Сергея миграции и полный набор 144 компаний уже применены. На другой БД импорт выполнять по [DATA_VALIDATION.md](DATA_VALIDATION.md). Существующие пароли сохраняются; для новых email seed запросит пароль 12+ символов (в Docker — DEMO_USER_PASSWORD), в том числе на заполненной БД. Не удалять базу или volumes. В существующем .env оставить DEMO_DATASET_DIR=demo_data/demo_0_3, остальные настройки/секреты сохранить. API не обновляет схему и не импортирует данные при старте.

Первый терминал:

```powershell
.\.venv\Scripts\python.exe -m credit_cabinet
```

Второй терминал:

```powershell
cd C:\alpha\alpha-hakaton\frontend
npm run dev
```

Если npm отсутствует в PATH, использовать уже установленный Node, как раньше:

```powershell
cd C:\alpha\alpha-hakaton\frontend
& 'C:\Users\user\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe' .\node_modules\vite\bin\vite.js
```

Открыть http://localhost:5173. Приемку делать на новой заявке: старые заявки намеренно сохраняют прежний продукт. GET /api/products через Swagger: первым идет version=3, annual_rate_percent=20.000, max_term_months=60, пять целей. При наличии прежнего продукта он может быть вторым для чтения старых черновиков.

## 2. Срок, цели, скидки и сохранение

Войти client@example.com, C01. В новой заявке выбрать оборудование, сумму 1000000, срок 60. Разрешить демо-проверку истории, дождаться сохранения. Ниже все числа относятся к исходной C01 нового набора: зрелая компания, чистая история, стабильные поступления, действующий кредит нашего банка.

| Параметры C01 | Ставка | Платёж |
| --- | --- | --- |
| INVENTORY, 1000000, 12 месяцев, без партнёра | 20% | 92634,51 |
| OTHER, 1000000, 36 месяцев, без партнёра | 21,5% | 37932,27 |
| EQUIPMENT, 1000000, 60 месяцев, партнёр | 22% | 27618,91 |
| EQUIPMENT, 1000000, 12 месяцев, партнёр | 20% | 92634,51 |

1. Для оборудования/60 месяцев отметить партнёра. Открыть «Из чего сложилась ставка»: база 20%, срок +4, цель −1, исправный заёмщик −0,5, партнёр −0,5 → 22%. UI округляет крупный платеж до рублей; API и банковский расчет хранят копейки.
2. Обновить страницу: цель, срок и флажок сохранились. Ввести 59: подпись «4 года 11 месяцев»; 60: «5 лет». В базе и API остаются месяцы. Проверить границы 6 и 60; 5/61 не позволяют подтвердить корректный срок.
3. Выбрать «Иное»: партнёрская опция исчезает и сохраняется false. Скидка за цель 0; описание можно оставить или заполнить, его слова не включают другую льготу. Остальные надбавки/банковская скидка продолжают действовать.
4. На оборудовании/12 месяцев с партнёром открыть расчет: доступно 2 п. п. скидок, но применено 0, так как база уже равна минимуму 20%. Для частичного ограничения можно взять 13 месяцев: до скидок 21%, применено 1 п. п., итог 20%.
5. На OTHER/24 месяца без партнёра сравнить варианты: REQUESTED и LOWER_AMOUNT — 20,5%, LONGER_TERM/36 месяцев — 21,5%. Срок и ставка меняются вместе; прежний платеж не используется.
6. Без согласия истории показывается ориентировочный базовый расчет с явным предупреждением, а не персональная ставка.

## 3. Отправка и банковский контур

1. Отправить оборудование/1000000/60/партнёр. Ожидается APPROVED, риск-балл 0, ставка 22%, платеж 27618,91. Войти сотрудником со своим действующим паролем, открыть «Решения» и эту заявку.
2. Во вкладке «Оценка» разложение ставки совпадает с клиентским. В «Данные заявки» партнёр указан как заявленный клиентом и непроверенный. В продукте 20% — база, а не ошибочно показанная персональная ставка.
3. Для ручного решения создать отдельную C01 на OTHER/2500000/12 месяцев, без партнёра. Ожидается MANUAL_REVIEW, балл 40, ставка 20%. Под сотрудником проверить дозапрос/повторную отправку и одобрение: решение сохраняет рассчитанную ставку, сотрудник не вводит ее вручную.
4. Открыть старую отправленную заявку demo-0.2: ставка/платеж/снимок остались прежними. Старый черновик можно завершить на 24% и сроке до 24 месяцев; для новых условий создать новую заявку.

## 4. AI и проверка API

На редактируемой заявке OTHER/24 месяца нажать «Сравнить варианты». При готовом Ollama ожидается SUCCESS и модель qwen2.5:1.5b. В ответе POST advisor есть факторы *_PRICING, разные ставки в scenarios и правильное фактическое снижение. Изменить цель или партнёрский признак: старый отчет должен стать неактуальным. Модель не назначает скидки.

Для банковского чтения нужен отчет по отправке, не по черновику. После отправки, оставаясь клиентом, через Swagger получить актуальную version и POST /api/applications/{id}/advisor с mode=EXPLAIN. Затем под банком вкладка «AI-разбор» покажет отчет с revision_id. Автоматического переноса чернового отчета нет.

В Swagger: PATCH принимает draft_data.purchase_from_bank_partner=true/false и expected_version. OTHER/OPERATING_EXPENSES с true → 422. Передача annual_rate_percent или has_active_loan_in_our_bank → 422. Неверная версия → 409. Проверки CSRF/Origin остаются прежними.
