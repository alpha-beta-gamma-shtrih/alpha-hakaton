# Синтетические данные demo-0.2

В [demo_0_2](demo_0_2/) подготовлен минимальный воспроизводимый набор C01/C02 — основа для проверки backend и продолжения работы Валерой/Софией. Это subset=C01_C02_BOOTSTRAP, не полный набор C01–C08 и не банковские реальные данные.

Контракт — [SYNTETIC.md](../SYNTETIC.md), проверка/импорт — [DRAFTS_CHECK.md](../DRAFTS_CHECK.md). Набор содержит две компании, 12 финансовых строк, четыре демо-пользователя, две membership-связи, один WC_DEMO/version=2, подготовленные юридические/кредитные ответы и сценарии, два CSV-шаблона документов.

## Как продолжать Валере и Софии

- Валера: companies.csv, financial_months.csv, demo_users.json, memberships.csv, documents/*.csv. Сначала сохранить C01/C02, затем добавить C03–C08 по утвержденным числам. Неполный профиль C04 не заполнять нулями.
- София: fns_responses.json, bki_responses.json и scenarios.json. В scenarios лежат будущие ожидаемые результаты; сейчас API не вычисляет и не возвращает их.
- manifest.json: schema_version=2, dataset_version=demo-0.2, policy_version=demo-policy-0.2; календарь/namespace сохраняются. После полного набора subset=FULL и company_keys дополняются.
- Форматы DTO для файлов находятся в src/credit_cabinet/schemas/seed.py. Для FNS SUCCESS поле is_bankrupt обязательно, значение bool/null; отсутствие не заменяется false.
- Все файлы — UTF-8 без BOM и LF; .gitattributes закрепляет LF для CSV/JSON. Деньги — строки с точкой и двумя знаками. CSV имеет точные заголовки из текущего примера.
- После изменения файла обновить его SHA-256 по реальным байтам в manifest.files; если это шаблон документа, также document_templates[].content_sha256. Manifest не хеширует сам себя. Никаких паролей/хешей/сессий в JSON пользователей.

Команда проверки без БД:

```powershell
.\.venv\Scripts\python.exe -m credit_cabinet.seed --check-only
```

Она проверяет версии, календарь, SHA-256, колонки/типы, ссылки между ключами, дубли, метаданные источников и базовую структуру fixtures. Она не доказывает правильность ожидаемого скоринга: реализация скоринга появится следующим этапом. Содержимое документов и будущая обработка fixtures будут дополнительно проверяться предметным кодом.

## Правила импорта для Сергея и Димы

```powershell
.\.venv\Scripts\python.exe -m credit_cabinet.seed
```

Без --check-only нужна настроенная .env и примененная миграция. Для новых аккаунтов пароль берется из DEMO_USER_PASSWORD или запрашивается скрытым вводом. Существующие email с той же ролью переиспользуются с прежним UUID и паролем. Роль не меняется автоматически.

UUID новых записей детерминированы через uuid5(namespace, ключ сущности). Одна транзакция; PostgreSQL-сериализация init через advisory lock. Повторный импорт добавляет только отсутствующее: не удаляет заявки, не сбрасывает пользователей/профили, не меняет конфигурацию существующей версии продукта. Конфликт профиля компании/условий версии/роли приводит к откату с ошибкой, а не скрытой замене. Финансовые строки, включая DECLARED, и состояние is_active продукта сохраняются.

В этом этапе в БД импортируются профили, финансы, продукт, пользователи и membership. Файлы документов/ФНС/БКИ/scenarios проверяются как часть поставки, но записи checks/decisions/documents еще не создаются. При отправке будущая реализация подключит подготовленные документы и источники.
