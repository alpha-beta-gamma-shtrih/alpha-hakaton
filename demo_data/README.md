# Синтетические данные кредитного кабинета

Рабочий набор — **[demo_0_3](demo_0_3/), subset=FULL**: 144 компании, 862 финансовые строки, 146 пользователей, 144 клиентские связи, один WC_DEMO/version=3, 144 ответа ФНС, 145 ответов БКИ, 18 сценариев и 144 CSV-документа. Архив Валеры адаптирован к действующему backend; отчёт об исправлениях, логины, ожидаемые результаты и пошаговая проверка — [DATA_VALIDATION.md](../DATA_VALIDATION.md).

[demo_0_2](demo_0_2/) — неизменённый исторический C01/C02, subset=C01_C02_BOOTSTRAP. Он нужен для воспроизведения старых условий и регрессионных тестов. Актуальные условия и версии — [PRICING.md](../PRICING.md), базовые форматы — [SYNTETIC.md](../SYNTETIC.md), DTO файлов — src/credit_cabinet/schemas/seed.py.

## Состав рабочего набора

| Файл | Назначение |
| --- | --- |
| companies.csv | Профили C01–C144; ключи C01/C02 и их рабочие реквизиты сохранены |
| financial_months.csv | Поступления, операционные расходы и существующий платёж за апрель–сентябрь 2026; C04 без июня, C09 без периода до регистрации |
| demo_users.json, memberships.csv | Один CLIENT на компанию, два BANK_STAFF без membership; пароли отсутствуют |
| credit_products.json | Только разрешённая текущая версия продукта; правила не настраиваются под профиль |
| bank_relationships.json | Демо-признак кредита в нашем банке; true только у C01, прочие false |
| fns_responses.json, bki_responses.json | Локальные ответы источников, включая ERROR/run_no=1 и SUCCESS/run_no=2 у C06 |
| scenarios.json | Параметры и проверочные результаты 18 отправок, включая персональные ставки; expected_result не управляет API |
| documents/*.csv | По одному отчёту FINANCIAL_STATEMENT на компанию, согласованному с её seed-финансами |
| manifest.json | schema_version=2, dataset_version=demo-0.3, policy_version=demo-policy-0.3, фиксированный календарь и SHA-256 файлов |

Дата расчёта — 01.10.2026; окно финансов — апрель–сентябрь. Неполнота не заменяется нулями. Вымышленные ИНН/регистрационные номера соответствуют демо-контракту длины, а не реестрам. Источники сохраняют версии legal-mock-0.2 и bki-mock-0.2: изменение ценообразования не меняет формат ответа источника.

## Проверка и импорт

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m credit_cabinet.seed --dataset demo_data/demo_0_3 --check-only
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m credit_cabinet.seed --dataset demo_data/demo_0_3
```

Проверка без БД ожидает valid=true, subset=FULL, companies=144. Она проверяет хеши, форматы, уникальность, ссылки, календарь, допустимость параметров сценария, наличие документов всех компаний и совпадение их строк с финансовым CSV. Расчёты и реальные API-переходы проверяют tests/test_expanded_data.py и tests/test_expanded_data_postgres.py.

При первом появлении новых email пароль берётся из DEMO_USER_PASSWORD либо запрашивается скрытым вводом: 12–1024 символа. Это пароль новых аккаунтов приложения, а не PostgreSQL. Существующие аккаунты сохраняют UUID и пароль. Для новых C03–C144 логины client3@example.com … client144@example.com; C01/C02 остаются client@example.com и client2@example.com. Сотрудники: bank@example.com и bank2@example.com.

Нужны настроенная .env и миграция 0005_personal_pricing. Импорт — одна транзакция с advisory lock PostgreSQL. Он добавляет отсутствующие записи, сохраняет финансовые правки пользователя, старые заявки/снимки/пароли и состояние is_active продукта. Конфликт компании, роли или неизменяемых условий продукта откатывает импорт. Банковский признак синхронизируется из sidecar. Повторный seed должен дать created=0 по всем категориям.

В БД загружаются пользователи, профили, финансовые месяцы, membership и продукт. Fixtures и шаблоны остаются файлами DEMO_DATASET_DIR, который нужен работающему API. При создании заявки её отчёт копируется в приватный DOCUMENTS_DIR; в БД сохраняются метаданные, а снимок фиксирует ссылки и хеши. Скачивание — только авторизованный GET /api/documents/{id}. Изменения финансов в форме не переписывают исходный CSV.

## Правки следующего набора

- Сохранять C01/C02, user_key, email и UUID namespace. Новая независимая компания — отдельные company_key/ИНН; чужой ИНН не использовать для другого сценария.
- Придерживаться точных DTO, UTF-8 без BOM и LF. Деньги — строки с точкой и двумя знаками. CSV — с точными заголовками, без индекса/комментариев/паролей.
- У каждой компании должны быть клиентская membership, ФНС, БКИ, банковский флаг и один финансовый отчёт. BANK_STAFF не привязывать к компаниям.
- После правки пересчитать manifest.files; для документа также document_templates[].content_sha256. Manifest не хеширует себя. Для финансов одновременно обновлять соответствующий документ, не меняя сохранённые копии существующих заявок.
- Недоступный источник: normalized_data=null. Для SUCCESS is_bankrupt обязателен как bool/null; отсутствие знания не означает false. При history_present=false числовые показатели БКИ нулевые.
- Попытки ответов уникальны по company_key/revision_no/run_no. revision_no=null задаёт общий профиль, явная версия имеет приоритет; выбирается последняя попытка не выше run_no оценки. GET и /scenarios попыток не расходуют.
- Никаких fixture_overrides в сценариях или исключений в правилах по company_key. Изолированные факты оформлять отдельным профилем либо согласованной попыткой источника. Сверять результат реальным движком и API.
- Обновление Docker: сохранить volumes, собрать образ с полным набором, выполнить миграции/seed и перезапустить API по [DOCKER_HANDOFF.md](../DOCKER_HANDOFF.md).
