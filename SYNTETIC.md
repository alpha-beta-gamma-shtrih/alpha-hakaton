# Действующий контракт формы, синтетики и решений: demo-0.2

Дата контракта: 20 октября 2026 года; статус обновлен 21 октября. Согласованный командой контракт demo-0.2 для передачи участникам. Приняты четыре уточнения: состав денежных показателей, отдельное демо-подтверждение БКИ, юридический факт банкротства и происхождение данных. Начало реализации backend разрешено. В demo_data/demo_0_2 подготовлен минимальный набор C01/C02 с subset=C01_C02_BOOTSTRAP; Валера и София расширяют его по этому контракту до C01–C08. Импорт, черновики, отправка/снимки, локальные источники/скоринг, автоматический дозапрос/новая отправка, технический retry и калькулятор реализованы; проверка — SUBMISSION_CHECK.md. Банковская очередь/карточка, просмотр версий/проверок, ручной дозапрос/решение реализованы; проверка — BANK_CHECK.md. Демо-документы подключены по DOCUMENTS_CHECK.md. AI-помощник реализован по AI_CHECK.md без расширения согласованного объема.

Этот файл дополняет принятую архитектуру, не заменяет ее: [ARCHITECTURE.md](ARCHITECTURE.md), [DATABASE.md](DATABASE.md), [USER_FLOWS.md](USER_FLOWS.md). Связанные документы согласованы с этой версией. Этот файл — единый источник конкретных полей формы, форматов синтетики, числовых правил, кодов причин и ожидаемых результатов; остальные документы ссылаются на него. Все условия, признаки и пороги ниже придуманы для воспроизводимого демо; это не правила Альфа-Банка, не оцененная PD и не подтвержденная модель кредитного риска.

## 2. Где физически находится синтетика

Разделяем исходный набор, работающий продукт и ожидаемые результаты тестов.

| Слой | Место после начала реализации | Назначение |
| --- | --- | --- |
| Исходные синтетические записи | demo_data/demo_0_2 в репозитории | Версионируемый воспроизводимый набор для подготовки демо |
| Профили и рабочие заявки | PostgreSQL, данные в Docker volume | Вход, предзаполнение, черновики, отправки, проверки, решения, история и AI-отчеты |
| Ответы ФНС/БКИ | Fixture-файлы, доступные backend внутри контейнера | Локальные адаптеры выбирают ответ по синтетической компании и номеру вызова |
| Подготовленные документы | demo_data/demo_0_2/documents, только синтетические CSV | Содержимое файла; в БД метаданные и ссылки |
| Ожидаемые результаты | Файл сценариев рядом с данными | Проверка корректности реализации; не вход кредитного решения |
| Веса нейросети | Отдельный volume Ollama | Не синтетический датасет и не содержимое PostgreSQL |

Поток данных: исходные файлы → init/импорт → PostgreSQL → API → frontend. Во время работы UI читает данные через API, не открывает CSV из репозитория. Рабочие правки не перезаписывают исходные CSV. Повторный init не сбрасывает созданные заявки. Сброс демо — отдельное явное действие, которое документируется позже.

Локальные адаптеры читают fixtures и сохраняют полученные результаты в check_results. Ожидаемый исход из сценария не передается в алгоритм решения. Нельзя реализовать «если company_key=C01, одобрить».

### Состав папки (минимальный C01/C02 уже создан)

| Файл | Формат и содержимое |
| --- | --- |
| manifest.json | Версия схемы/набора, policy_version, seed, calculation_date, список файлов, метаданные шаблонов документов и параметры детерминированного импорта |
| companies.csv | Одна строка на синтетическую компанию |
| financial_months.csv | Одна строка на компанию и месяц |
| credit_products.json | Одна версия демонстрационного продукта и параметры политики |
| demo_users.json | Вымышленные email, имена, роли и user_key; без реальных паролей и password_hash |
| memberships.csv | Связи user_key/company_key |
| fns_responses.json | Сценарные ответы локальной ФНС |
| bki_responses.json | Сценарные ответы локального БКИ |
| scenarios.json | Параметры проверяемых действий, отдельные сценарные переопределения fixtures и ожидаемые результаты |
| documents/*.csv | Подготовленные документы с вымышленными финансовыми показателями |

CSV: UTF-8, запятая-разделитель, заголовок, стандартное экранирование кавычками. JSON: UTF-8, имена полей snake_case. Деньги в обоих форматах — десятичные строки с точкой и двумя знаками, без пробелов и символа валюты. Пустая ячейка CSV преобразуется в null; не в ноль. Даты — YYYY-MM-DD, месяц — первое число.

company_key вида C01 и user_key — ключи обмена файлами, не UUID из API. Импорт детерминированно сопоставляет их UUID по зафиксированному namespace. Ксюша получает id из API, не подставляет C01 вместо company_id. Демонстрационные пароли задаются настройкой подготовки демо и хешируются backend; файл пользователей не содержит производственных учетных данных.

Сценарный выбор ошибки/ответа — механизм fixtures и тестового запуска. Обычный клиентский API не принимает поля force_approve, scenario_id или bki_error, влияющие на рассмотрение.

## 4. Контракт формы

### 4.1. Шаги

1. NEED: цель, сумма, срок и предварительный расчет.
2. COMPANY: выбранная компания и сведения для подтверждения.
3. FINANCES: шесть месяцев показателей и обнаруженные пробелы.
4. REVIEW: итог, документы, отдельные подтверждения сведений и демонстрационной проверки БКИ, отправка.

AI-помощь находится внутри подбора. Она использует тот же черновик и не создает вторую независимую анкету. Документы в работающем демо будут подготовлены из набора; кнопка произвольной загрузки не требуется. Стресс-сценария и дополнительных AI-функций в demo-0.2 нет.

### 4.2. Изменяемые поля и типы

| Путь в API | Вид поля | Черновик | Условие отправки и бизнес-проверки |
| --- | --- | --- | --- |
| company_id | Выбор доступной компании при создании | Обязателен при создании | Только компания по membership; далее в этой заявке не меняется |
| product_id | Выбор версии продукта из API | Обязателен при создании | Активная версия WC_DEMO; id задает API |
| requested_amount | Денежная строка | Может быть null | Обязательно, 100000.00–5000000.00 |
| term_months | Целое число/ползунок | Может быть null | Обязательно, 6–24 |
| purpose_code | Select | Может быть null | Обязательно, одно из трех значений ниже |
| purpose_details | Textarea | Необязательно | Строка до 1000 символов |
| draft_data.financial_months | Таблица месяцев | Может быть неполной | Неполнота ведет к NEEDS_INFO, а не к выдуманным нулям |
| draft_data.financial_months[].month | Месяц строки | Для имеющейся строки обязателен | Только шесть месяцев окна, без дублей |
| draft_data.financial_months[].cash_inflow | Денежная строка | Может быть null | Поступления от деятельности; без полученных кредитов, взносов собственника и внутренних переводов |
| draft_data.financial_months[].operating_outflow | Денежная строка | Может быть null | Реальные операционные выплаты и моделируемые налоги; без платежей по долгам и внутренних переводов |
| draft_data.financial_months[].existing_debt_payment | Денежная строка | Может быть null | Платежи по действующим долгам: тело и проценты, не остаток долга; отсутствие платежа — 0.00 |
| draft_data.confirmations.data_confirmed | Checkbox | false или отсутствует | true перед отправкой; подтверждение данных, не юридическая электронная подпись |
| draft_data.confirmations.credit_history_check_allowed | Checkbox | false или отсутствует | true перед обращением к БКИ-симулятору и перед отправкой; отдельное демо-подтверждение |
| draft_data.info_response | Textarea при дозапросе | Необязательно | До 1000 символов; может дополнять исправленные поля, не заменяет их |
| ui_step | Служебное значение | NEED / COMPANY / FINANCES / REVIEW | Только разрешенное значение; не влияет на скоринговые факты |

Цели: INVENTORY — «Закупка товара/материалов»; OPERATING_EXPENSES — «Текущие расходы бизнеса»; SEASONAL_PURCHASE — «Закупка к сезону». Ксюша показывает подписи, backend получает коды.

В шаге COMPANY отображаются legal_name, legal_form, inn, registered_on, okved_code и region_code из API. В demo-0.2 они не редактируются в форме. Текущие вопросы про финансовые показатели меняют только draft_data заявки, не общий профиль компании. В одном месяце лимит каждой суммы 9999999999999999.99; NaN, Infinity, отрицательные значения и больше двух знаков после точки отклоняются, не округляются молча.

Пустое поле — null, не пустая строка и не 0.00. Месяцы отображаются в хронологическом порядке. API сохраняет частичный ввод, но не некорректные типы. Отправка за пределами лимитов продукта дает 422 и ошибку поля, а не REJECTED.

Если основные параметры и оба подтверждения заполнены, но история неполная, можно отправить имеющиеся сведения с явным предупреждением «Для решения потребуется уточнение». Backend создает отправку и NEEDS_INFO. Для этой ветки UI не блокирует кнопку только из-за отсутствующего финансового месяца. Некорректный формат/отрицательная сумма по-прежнему блокируют отправку как ошибка формы.

### 4.3. Подтверждение БКИ и его фиксация

Снимки и текущий черновик не смешиваются: изменение флага в черновике не аннулирует записи уже выполненного демо-рассмотрения; юридический отзыв согласия в этом MVP не моделируется.

Текст checkbox: «Подтверждаю запуск демонстрационной проверки кредитной истории. Используются только синтетические данные». Он связан с одним полем формы: основное место REVIEW, а при раннем обращении к AI тот же элемент доступен в блоке подбора. Это не два независимых подтверждения.

- Оба confirmations-поля принимают только BOOLEAN. Только явное true разрешает соответствующее действие; отсутствие, null или false не заменяются true при предзаполнении, импорте либо ответе AI.
- Отправка без credit_history_check_allowed=true возвращает 422, code=CREDIT_HISTORY_CONFIRMATION_REQUIRED и field_errors с путем draft_data.confirmations.credit_history_check_allowed. Не создаются новая application_revision, assessment, запрос БКИ и финальный отказ. Проверка доступа и уже выполненного повтора submission_key по-прежнему предшествует созданию нового действия.
- Без подтверждения /scenarios может вернуть только расчет платежа/переплаты по сумме и сроку: load_ratio, risk_score и preliminary_route равны null, reason_codes содержит CREDIT_HISTORY_CONFIRMATION_REQUIRED. Источники ФНС/БКИ в этом ограниченном режиме не вызываются.
- Без подтверждения /advisor возвращает 422 с той же причиной и подсказкой; БКИ, LLM и новый advisor_report не запускаются. Это состояние формы, не отказ модели и не кредитное решение.
- При отправке backend сохраняет confirmations в financial_snapshot.confirmations. Подтвердивший пользователь — submitted_by_user_id, время фиксации — серверный created_at этой отправки. Отдельная таблица согласий и время с браузера не нужны.
- Для PREVIEW проверяется текущий черновик; для официального рассмотрения и банковского повтора — confirmations рассматриваемой отправленной версии. Неотправленные правки не подменяют ее входы.
- При изменении флага в черновике старые отправки не переписываются. Отчет, использующий кредитную историю, не показывается как текущий для черновика без подтверждения; input_hash учитывает значение флага.
- Это имитация шага процесса, не юридически действительное согласие/электронная подпись и не реальное подключение к БКИ.

### 4.4. Что возвращает API

Текущий этап реализует черновики/события, submit, клиентское чтение снимка/решения, scenarios и банковский retry-processing. У редактируемой заявки доступны EDIT_DRAFT/SUBMIT; в финале действий клиента нет. Банковские очередь/карточка/версии/история, request-info, decision и advisor уже подключены; проверка AI — AI_CHECK.md. У сотрудника отдельные DTO, они читают revision, а не текущие правки клиента. Submit возвращает application/revision/assessment; GET заявки содержит latest_revision_id/no и assessment. Списки компаний/продуктов/заявок имеют envelope items/total/limit/offset; история событий — items без пагинации. Все суммы и исходные границы сохраняют demo-0.2; конкретные примеры — DRAFTS_CHECK.md и SUBMISSION_CHECK.md.

| Поле | Смысл |
| --- | --- |
| id, company_id, product_id | Идентификаторы приложения |
| status, version | Текущий статус и lock_version |
| requested_amount, term_months, purpose_code, purpose_details | Параметры заявки |
| draft_data, ui_step | Разрешенные данные формы и шаг |
| calculation_date, policy_version | Контекст расчета |
| provenance | Источники и даты разрешенных групп фактов по разделу 5.6; без неразрешенных данных БКИ |
| allowed_actions | Список разрешенных действий, не решение frontend по названию роли |
| open_information_request | null либо id, message_to_client, requested_fields |
| decision | null либо клиентский итог без internal_comment |
| updated_at | ISO 8601 UTC |

allowed_actions в этой версии: EDIT_DRAFT, SUBMIT, REQUEST_INFO, APPROVE, REJECT, RETRY_PROCESSING. Действия банка вычисляются по последней отправке/оценке и повторно проверяются при команде с блокировкой/version; manual decision задает только outcome/public_explanation/internal_comment, без замены условий. Для ручного итога добавлены MANUAL_APPROVED/MANUAL_REJECTED; факторы сохраняются, предварительная причина BORDERLINE_RISK не выдается как отсутствие уже принятого решения. Клиент получает только EDIT_DRAFT/SUBMIT, когда это допустимо; сотрудник — свои действия. Чтение разрешенных данных не требует отдельной кнопки в этом списке.

Маршруты сохраняются из архитектуры: POST /api/applications; GET/PATCH /api/applications/{id}; POST /api/applications/{id}/submit; POST /api/applications/{id}/scenarios; POST /api/applications/{id}/advisor.

PATCH содержит expected_version и только разрешенные изменяемые поля. Поля отсутствуют — оставить как есть; null — очистить nullable-поле. financial_months при наличии в PATCH целиком заменяет массив месяцев: frontend отправляет актуальный массив, не скрытый merge по позиции. draft_data обновляется по известным ключам; остальные ключи сохраняются. Допускаются только financial_months, confirmations и info_response; в confirmations — только data_confirmed и credit_history_check_allowed. При частичном обновлении confirmations неуказанный флаг сохраняется. Неизвестные поля дают 422. provenance и is_bankrupt клиентом не записываются. PATCH не меняет роль, компанию, продукт, статус и серверные результаты.

При отправке передаются expected_version и submission_key (UUID). При повторе после потери ответа используются тот же ключ и тот же ожидаемый вход: backend находит уже созданную отправку и возвращает ее актуальный результат, прежде чем отклонять повтор из-за выросшей версии. Новый ключ со старой версией — 409. Ответы на автосохранение обрабатываются последовательно.

Формат ошибки: code, message, field_errors с путями полей, request_id. Для 401 нужен повторный вход, для 409 — актуальное состояние, для 422 — исправление полей. Клиент не передает risk_score, outcome, model_output или результаты ФНС/БКИ.

GET /api/products передает id, code, version, name, min_amount, max_amount, min_term_months, max_term_months, annual_rate_percent, currency, allowed_purposes и policy_version. Валюта RUB задается этим контрактом; отдельный столбец продукта для нее в demo-0.2 не нужен. GET /api/companies/{id} передает разрешенный профиль и исходные financial_months. Ксюша берет ограничения и предзаполнение из API, не дублирует их скрытой второй конфигурацией.

### 4.5. Объяснения для клиента

Backend возвращает причины как объекты code/message и при необходимости field_paths; численные факторы/вклады сохраняются в оценке, а внутренние комментарии отделены. В интерфейсе допустимо уточнить стилистику следующих подписей без изменения кодов:

| Код или группа | Клиентский смысл |
| --- | --- |
| DEMO_POLICY_PASSED | Заявка прошла демонстрационные правила; для PREVIEW это только предварительный результат |
| CREDIT_HISTORY_CONFIRMATION_REQUIRED | Подтвердите запуск демонстрационной проверки истории; платеж уже можно рассчитать |
| COMPANY_BANKRUPTCY | Юридическая демо-проверка выявила признак банкротства, несовместимый с условиями продукта |
| LEGAL_STATUS_UNCONFIRMED | Юридические сведения пока не подтверждены; нужен разбор, итогового решения нет |
| FINANCIAL_HISTORY_INCOMPLETE | Дополните отмеченные месяцы и показатели |
| DEBT_PAYMENT_MISMATCH | Уточните текущие платежи: заявленные сведения и проверка расходятся |
| SOURCE_FNS_UNAVAILABLE / SOURCE_BKI_UNAVAILABLE / SOURCE_RESPONSE_INVALID | Проверку пока не удалось завершить; это не кредитный отказ |
| COMPANY_DATA_MISMATCH | Требуется уточнить сведения о компании при рассмотрении |
| COMPANY_NOT_ACTIVE | Статус компании не соответствует условиям демонстрационного продукта |
| BUSINESS_TOO_YOUNG | Возраст бизнеса меньше шести месяцев, установленных в демо-продукте |
| CURRENT_OVERDUE / SEVERE_OVERDUE_HISTORY | Обнаружена текущая или существенная историческая просрочка в синтетических данных |
| NON_POSITIVE_CASHFLOW | Средний денежный поток до обслуживания долга неположительный |
| DEBT_LOAD_LIMIT_EXCEEDED | Расчетные платежи превышают предел нагрузки демонстрационной политики |
| TREND_BASELINE_ZERO | Для расчета тренда нужны уточнения по исходному периоду |
| BORDERLINE_RISK | Нужна оценка сотрудника; итогового решения еще нет |
| RISK_SCORE_LIMIT_EXCEEDED | Сочетание факторов превышает порог демонстрационной политики |
| Факторные коды раздела 8 | Объясняют возраст, нагрузку, падение поступлений или историю; не являются отдельным новым решением |

Клиентские сообщения не содержат stack trace и не называют придуманные пороги действующей политикой банка. Ошибка источника и отказ визуально различаются. Нельзя заменять подпись PREVIEW на «Одобрено» ради оформления карточки.

## 5. Требования к исходным данным

### 5.1. Компании и учетные записи

companies.csv: company_key, legal_name, legal_form, inn, registration_number, registered_on, okved_code, region_code, business_description. Все названия явно вымышленные. Для IP — 12 цифр ИНН, OOO — 10; проверку контрольных разрядов в demo-0.2 не включаем. Даже корректный формат не означает, что реквизиты никогда не совпадут с реальными: набор помечен DEMO, внешних запросов нет.

demo_users.json: user_key, email, display_name, role, is_active. Минимум один клиент на компанию и два сотрудника для проверки одновременного решения. memberships.csv: user_key, company_key. Серверные сессии не поставляются в исходных данных.

### 5.2. Финансовая история

financial_months.csv: company_key, month, cash_inflow, operating_outflow, existing_debt_payment, source. source=DEMO. Одна строка на месяц и компанию, без дублей; в нормальном профиле ровно шесть месяцев. Для сценария неполноты допускается намеренный пробел, помеченный в scenarios.json. Импорт проверяет структуру, но не «исправляет» такой пробел нулевыми данными и не отклоняет весь набор.

Периоды не находятся раньше регистрации бизнеса. Все суммы неотрицательны и в рублях. cash_inflow содержит только операционные поступления; полученные кредиты, взносы собственника и переводы между своими счетами исключаются. operating_outflow содержит реальные операционные выплаты и моделируемые налоги, исключая внутренние переводы и existing_debt_payment. existing_debt_payment включает тело и проценты, не остаток долга. Расходы не включают existing_debt_payment второй раз. Суммы отражают фактические денежные операции, включая НДС там, где он присутствует в платежах. Отдельной модели начисления/вычета НДС нет; теоретический НДС поверх введенных выплат не добавляется. Отрицательный денежный поток образуется превышением расходов над поступлениями, а не отрицательной суммой выручки. Для базовых профилей используем одинаковые суммы по месяцам; отдельный сценарий проверяет тренд.

### 5.3. Симулятор ФНС

Оболочка ответа: company_key, status (SUCCESS / NO_DATA / ERROR), error_code, source_version, normalized_data, provenance. source_version=legal-mock-0.2. При ERROR/NO_DATA normalized_data=null, не вымышленный успешный объект.

normalized_data для SUCCESS: inn, legal_form, registered_on, registry_status, is_bankrupt. registry_status: ACTIVE / LIQUIDATING / CLOSED. is_bankrupt: true / false / null. true — установленный демо-признак банкротства; false — отрицательный результат именно этой проверки; null или отсутствие — факт неизвестен, не false. Это консолидированный локальный юридический адаптер в существующем слоте FNS; не описание настоящего API ФНС и не утверждение о полноте одного реестра. В базовых профилях регистрационные данные совпадают с профилем компании. Даты/идентификаторы конфликтуют только в явно описанном негативном сценарии.

### 5.4. Симулятор БКИ

Оболочка: company_key, status (SUCCESS / NO_DATA / ERROR), error_code, source_version, normalized_data, provenance. source_version=bki-mock-0.2. Для разных технических попыток fixture задает последовательность по revision_no/run_no, а не по числу HTTP-запросов пользователя. Предпросмотр и AI не расходуют технические попытки и не сдвигают ответ будущей официальной проверки.

| Поле normalized_data | Тип и смысл |
| --- | --- |
| history_present | BOOLEAN, есть подтвержденная кредитная история |
| current_monthly_payment | Денежная строка, текущие платежи по действующим обязательствам |
| max_overdue_days_12m | Целое неотрицательное число, максимум дней просрочки за 12 месяцев до calculation_date |
| current_overdue_amount | Денежная строка, текущая просроченная сумма |

SUCCESS + history_present=false — корректный ответ об отсутствии истории, а не ошибка источника. Для такого профиля три числовых поля равны нулю. NO_DATA означает отсутствие надежного ответа по поиску, а не доказательство хорошей истории; это отдельная ветка ручного разбора. Закрытая историческая просрочка может иметь ненулевые дни при current_overdue_amount=0.00.

### 5.5. Документы и сценарии

В documents достаточно CSV с месяцами и финансовыми показателями соответствующего исходного профиля. Метаданные шаблонов в manifest содержат company_key, тип FINANCIAL_STATEMENT, путь и контрольную сумму. Реализовано: при создании заявки backend создает связанные с application_id записи documents из этих шаблонов и приватные неизменяемые копии в DOCUMENTS_DIR; до создания заявки фиктивных связей нет. В нормальном исходном сценарии CSV совпадает с профилем. После редактирования финансов форма получает CLIENT_DECLARED, а файл остается исходным DEMO-профилем: он не подтверждает новый ввод, автоматической сверки и нового правила скоринга не добавляем. Специальные несоответствия исходного CSV самому профилю допустимы только как явно отмеченная проверка качества.

Формат CSV тот же, что financial_months.csv: company_key,month,cash_inflow,operating_outflow,existing_debt_payment,source. Только свой company_key, source=DEMO, без повторов месяца, месяцы из окна manifest; UTF-8/LF, максимум 2 MiB. Для каждого профиля нужен хотя бы один шаблон; путь documents/имя.csv, хеш совпадает в manifest.files и document_templates. Отправка сохраняет ID/метаданные/хеши в document_refs; банк получает только отправленные файлы через GET /api/documents/{id}. Измененные исходные шаблоны не заменяют файлы старых заявок. Подробная приемка — DOCUMENTS_CHECK.md.

scenarios.json содержит scenario_key, company_key, requested_amount, term_months, purpose_code, при необходимости исправления financial_months и явные fixture-overrides, sequence действий и expected_result. expected_result включает status, routing, risk_score либо null, reason_codes, monthly_payment и разрешенные действия. Секретного expected_result во входе решения нет.

### 5.6. Единый формат происхождения данных

provenance — объект групп фактов: company, financial_months и credit_history. Каждая доступная группа содержит source, as_of_date и checked_at; checked_at nullable. Неизвестная/недоступная группа — null. Сам конверт не означает успешную проверку: ее status находится в check_results.

| source | Смысл и подпись |
| --- | --- |
| DEMO_PROFILE | Исходные вымышленные сведения: «Демонстрационный профиль» |
| CLIENT_DECLARED | Измененный пользователем блок: «Указано пользователем» |
| MOCK_FNS | «Юридический демо-симулятор» |
| MOCK_BKI | «Демо-симулятор кредитной истории» |

Для financial_months as_of_date=2026-09-30 — конец окна; для юридических/кредитных fixtures as_of_date=calculation_date=2026-10-01. checked_at — реальное время завершенного локального вызова в UTC, а не подмена его демонстрационной датой. До вызова и у исходного профиля checked_at=null. В исходных fixture-файлах можно оставить checked_at=null: его ставит адаптер, не генератор будущего времени.

company_financial_months.source в существующей БД сохраняет значения DEMO/DECLARED: они отображаются в provenance как DEMO_PROFILE/CLIENT_DECLARED. Колонка check_results.source сохраняет DATA_QUALITY/FNS/BKI; MOCK_FNS/MOCK_BKI относятся к вложенному provenance, не заменяют enum колонки.

Метаданные шаблона финансов в manifest и envelope ответов источников задают происхождение; новую колонку в CSV на каждый факт не добавляем. После изменения финансов backend переводит provenance.financial_months в CLIENT_DECLARED, не доверяя присланному источнику. Реквизиты и финансовые показатели имеют отдельные группы. Результаты источников могут иметь проверенный normalized_data=null при ERROR; это не подтверждение фактов.

API отображает только разрешенные группы. До подтверждения БКИ credit_history=null и не содержит извлеченных/кэшированных сведений. Отправленная версия сохраняет financial_snapshot.provenance и company_snapshot.provenance; для успешных проверок provenance находится внутри существующего check_results.normalized_data; при ERROR/NO_DATA normalized_data остается null, источник/время/дата контекста берутся из source/source_version/completed_at и отправленного снимка; assessments.input_facts и advisor_reports.context_snapshot сохраняют происхождение использованных фактов. Сырые пароли и session tokens туда не попадают.

Функциональный input_hash учитывает значения, source/as_of_date, подтверждение БКИ, версию правил и используемую оценку. Изменение только ui_step или служебного checked_at не меняет финансовый результат. Поздние проверки не изменяют provenance уже отправленного снимка, а сохраняются в новых результатах. AI объясняет происхождение, не объявляет утверждение клиента реально подтвержденным банком.

## 6. Вычисляемые признаки и правила округления

Все вычисления на Decimal с внутренней точностью не менее 28 значащих цифр. Порог сравнивается с неокругленным отношением; округление для UI не меняет маршрут.

| Признак | Определение |
| --- | --- |
| business_age_months | Полные календарные месяцы от registered_on до calculation_date; неполный месяц не засчитывается |
| average_operating_cashflow | Среднее за 6 месяцев от cash_inflow минус operating_outflow, до обслуживания долга |
| declared_current_payment | existing_debt_payment последнего месяца, 2026-09-01 |
| confirmed_current_payment | current_monthly_payment успешного ответа БКИ |
| existing_payment | Максимум declared_current_payment и confirmed_current_payment, если они согласованы; не сумма двух описаний одного долга |
| new_monthly_payment | Аннуитетный расчет ниже, округленный до копеек ROUND_HALF_UP |
| load_ratio | (existing_payment + new_monthly_payment) / average_operating_cashflow при положительном знаменателе |
| inflow_trend | Средние поступления июля–сентября / средние поступления апреля–июня минус 1 |

Расхождение платежей: abs(declared_current_payment - confirmed_current_payment) > max(1000.00, 0.10 × max(declared_current_payment, confirmed_current_payment)). Равенство порогу не является расхождением. При расхождении нужен дозапрос, не выбор удобного меньшего значения.

Аннуитет: A = S × r / (1 - (1+r)^(-n)), где S — сумма, n — месяцы, r = annual_rate_percent / 100 / 12. Для ставки 24% r=0.02. В ветке нулевой ставки A=S/n; в текущем продукте ставка ненулевая.

A округляется до копеек до расчета load_ratio. Общий платеж для UI = A × n, примерная переплата = A × n - S. Корректировку последнего платежа и банковский календарь не моделируем; UI обозначает предварительный расчет. При average_operating_cashflow<=0 отношение не рассчитывается, деления на ноль нет.

## 7. Последовательность решения: первый сработавший маршрут

Сначала API проверяет доступ и структуру. Неизвестные/недоступные id, отсутствующие основные поля или любое обязательное подтверждение, неверные типы, отрицательные суммы, дубли месяцев, неверная цель, выход суммы/срока за продукт или неподтвержденные сведения — ошибка запроса, не кредитный отказ. Разбор по существу начинается после сохранения валидной отправленной версии.

| Порядок | Условие | Routing / статус | Основная причина |
| --- | --- | --- | --- |
| 1 | ФНС ERROR или NO_DATA | MANUAL_REVIEW | SOURCE_FNS_UNAVAILABLE |
| 2 | При SUCCESS данные inn/legal_form/registered_on противоречат профилю или ответ структурно некорректен | MANUAL_REVIEW | COMPANY_DATA_MISMATCH / SOURCE_RESPONSE_INVALID |
| 3 | ФНС registry_status=LIQUIDATING или CLOSED | REJECT / REJECTED | COMPANY_NOT_ACTIVE |
| 4 | is_bankrupt=true при согласованных действующих реквизитах | REJECT / REJECTED | COMPANY_BANKRUPTCY |
| 5 | is_bankrupt=null или отсутствует в контракте 0.2 | MANUAL_REVIEW | LEGAL_STATUS_UNCONFIRMED |
| 6 | business_age_months < 6 | REJECT / REJECTED | BUSINESS_TOO_YOUNG |
| 7 | БКИ ERROR или NO_DATA либо структурно некорректный ответ | MANUAL_REVIEW | SOURCE_BKI_UNAVAILABLE / SOURCE_RESPONSE_INVALID |
| 8 | current_overdue_amount > 0 | REJECT / REJECTED | CURRENT_OVERDUE |
| 9 | max_overdue_days_12m >= 60 | REJECT / REJECTED | SEVERE_OVERDUE_HISTORY |
| 10 | Отсутствует месяц окна или любое из трех его финансовых значений | NEEDS_INFO | FINANCIAL_HISTORY_INCOMPLETE |
| 11 | Платежи последнего месяца и БКИ расходятся сильнее допустимого | NEEDS_INFO | DEBT_PAYMENT_MISMATCH |
| 12 | average_operating_cashflow <= 0 | REJECT / REJECTED | NON_POSITIVE_CASHFLOW |
| 13 | load_ratio > 0.80 | REJECT / REJECTED | DEBT_LOAD_LIMIT_EXCEEDED |
| 14 | Средние поступления апреля–июня равны 0, тренд не определен | MANUAL_REVIEW | TREND_BASELINE_ZERO |
| 15 | Предыдущие проверки пройдены | Посчитать risk_score и применить раздел 8 | Согласно таблицам баллов |

На первом терминальном условии дальнейшее кредитное решение не рассчитываем. Например, технический сбой БКИ направляет сотруднику, не превращает нулевые отсутствующие поля в отсутствие долгов. Неактивная компания отклоняется по известному результату ФНС до рассмотрения состояния БКИ. Политика порядка вымышленная, но однозначная.

Для маршрутов 1–14 risk_score=null и risk_band=UNKNOWN: числовой скоринг еще не завершен, даже если сработало жесткое основание отказа. Статус и reason_code объясняют результат без подставного балла 100. Для NEEDS_INFO создается information_request с конкретными requested_fields; для MANUAL_REVIEW финального decision еще нет. Для REJECT создаются decision и событие в одной транзакции со сменой статуса.

## 8. Балльный скоринг после обязательных проверок

Шкала: больше баллов — выше демонстрационный риск. risk_score=min(100, сумма вкладов). Это не вероятность дефолта.

| Фактор | Условие | Баллы / reason_code |
| --- | --- | --- |
| Возраст | 6–11 полных месяцев | +20 / BUSINESS_AGE_6_11 |
| Возраст | 12–23 месяца | +10 / BUSINESS_AGE_12_23 |
| Возраст | >=24 месяцев | +0 |
| Нагрузка | load_ratio <=0.35 | +0 |
| Нагрузка | >0.35 и <=0.50 | +10 / LOAD_35_50 |
| Нагрузка | >0.50 и <=0.65 | +25 / LOAD_50_65 |
| Нагрузка | >0.65 и <=0.80 | +40 / LOAD_65_80 |
| Тренд поступлений | inflow_trend >=0 | +0 |
| Тренд | >=-0.15 и <0 | +5 / INFLOW_DROP_0_15 |
| Тренд | >=-0.30 и <-0.15 | +15 / INFLOW_DROP_15_30 |
| Тренд | <-0.30 | +25 / INFLOW_DROP_OVER_30 |
| История просрочек | max_overdue_days_12m=0 | +0 |
| История просрочек | 1–29 дней | +10 / OVERDUE_1_29 |
| История просрочек | 30–59 дней | +25 / OVERDUE_30_59 |
| Наличие истории | history_present=false при SUCCESS | +15 / CREDIT_HISTORY_ABSENT |

Суммируются только применимые строки; диапазоны одного фактора взаимно исключают друг друга. При отсутствии истории дни просрочки равны нулю, но отдельные +15 сохраняются.

| Итоговые баллы | risk_band | Routing / статус | Reason code |
| --- | --- | --- | --- |
| 0–29 | LOW | APPROVE / APPROVED | DEMO_POLICY_PASSED плюс ненулевые факторы |
| 30–59 | MEDIUM | MANUAL_REVIEW | BORDERLINE_RISK плюс факторы |
| 60–100 | HIGH | REJECT / REJECTED | RISK_SCORE_LIMIT_EXCEEDED плюс факторы |

Автоматическое одобрение относится к запрошенным сумме/сроку и ставке этой версии продукта. LLM не меняет балл, пороги, результаты проверок или финальный маршрут. Отказ по скорингу и технический ручной разбор имеют разные reason_codes.

## 9. Что разрешено сотруднику

| Причина MANUAL_REVIEW | Разрешенные действия |
| --- | --- |
| BORDERLINE_RISK, все обязательные проверки завершены | APPROVE, REJECT с обоснованием или REQUEST_INFO; нельзя выйти за условия рассматриваемой версии |
| Ошибка/нет надежного ответа источника | RETRY_PROCESSING; нет финального одобрения или отказа только из-за технической ошибки |
| Противоречивые сведения компании/некорректный ответ или LEGAL_STATUS_UNCONFIRMED | Разбор причины/повтор проверки; без обхода обязательной проверки и без подстановки is_bankrupt=false |
| Неопределенный тренд при нулевой базе | REQUEST_INFO; финальное решение только после появления определенных входов либо отдельного последующего уточнения политики |

В NEEDS_INFO отвечает клиент, затем выполняется новый расчет по новой отправке. Уже финальные APPROVED/REJECTED не переигрываются кнопкой сотрудника. В SUBMITTED после прерывания разрешен повтор обработки той же отправки. Для ручного отказа при BORDERLINE_RISK нужен содержательный комментарий, а не пустое «решил сотрудник».

## 11. Калькулятор и AI: контракт интерфейса

Для /scenarios backend рассматривает исходные параметры и до двух альтернатив: сумма 80% исходной с нижней границей продукта при том же сроке; срок +12 месяцев с верхней границей 24 при той же сумме. Сумма округляется до копеек. Дубли убираются. Варианты всегда проходят ту же валидацию и те же демонстрационные правила на тех же фактах компании; ни один не гарантируется подходящим заранее.

Полный PREVIEW доступен только при credit_history_check_allowed=true; без него действует расчетный режим раздела 4.3. Текущая AI-функция сохранена: объяснение, сравнение суммы/срока и недостающие данные. Стресс-тесты, новые источники, OCR/RAG и обучение модели не входят в demo-0.2.

Предпросмотр использует тот же неизменяемый набор фактов для всех кандидатов, не создает официальные assessments/check_results и не расходует ответы по run_no. При отсутствии сохраненной оценки адаптер может прочитать предусмотренное fixture-представление без побочных эффектов; источник и предварительность показываются явно. После получения официального результата сравнение опирается на него и имеет новый input_hash. Результат предварительного сравнения не подменяет последующие обязательные проверки отправленной версии.

Ответ варианта: candidate_id, requested_amount, term_months, annual_rate_percent, monthly_payment, estimated_total_payment, estimated_overpayment, load_ratio либо null, risk_score либо null, preliminary_route либо null в ограниченном режиме, reason_codes, provenance, policy_version, input_hash, is_binding=false. PREVIEW не меняет status и не создает финальный decision; вариант хранится в контексте AI-отчета при необходимости.

Клиентские подписи: APPROVE → «Проходит предварительные демо-правила»; MANUAL_REVIEW → «Потребуется рассмотрение специалиста»; NEEDS_INFO → «Нужно дополнить данные»; REJECT → «Не проходит текущие демо-правила». Слово «Одобрено» относится только к финальному статусу отправленной заявки.

В /advisor передается запрос по разрешенной заявке, не произвольные результаты скоринга из браузера. Backend сам собирает факты и рассчитанные варианты. Модель объясняет различия, ссылается на разрешенные factor_id/candidate_id, не рассчитывает условия заново и не обещает выдачу. Кнопка «Выбрать эти параметры» сохраняет выбранную сумму/срок в черновик с expected_version; отправка остается отдельным действием.

Если не хватает данных или источник недоступен, AI объясняет пробел и следующий шаг, не выдумывает список доступных кредитов. Ошибка/таймаут LLM приводит к явному fallback с расчетами backend. Числа в UI берутся из backend. Реализация: модель выбирает только разрешенные factor_id/candidate_id, а backend определяет следующий шаг и составляет текст из проверенных карточек; свободных утверждений модели о кредитных условиях нет. POST advisor принимает expected_version и mode=EXPLAIN/COMPARE. Отчеты сохраняются, GET возвращает is_current; банк читает только отчеты по revision. Явный FALLBACK сохраняет расчеты и не выдается за SUCCESS. Полный контракт — AI_CHECK.md.

## 12. Приемка синтетики и границы

Валера и София передают небольшой проверенный набор, не тысячи случайных строк. Должны выполняться:

- Одинаковый seed/manifest и импорт дают те же company/user UUID, финансовые признаки и исходы. Для повторной репетиции сценарная последовательность ответов источника явно сбрасывается; ее не скрывает случайный счетчик в процессе API.
- Для обычных отправок оба confirmations=true; отказ от проверки БКИ не вызывает источник, LLM или отказ в кредите. is_bankrupt проверяется как true/false/null, пропуск не становится false.
- provenance соответствует источникам; checked_at не подменяет as_of_date, клиент не может записать MOCK_BKI. Изменение финансов снимает ложную подтвержденность.
- AI не содержит стресс-сценария и не использует кредитную историю через кэш при отсутствующем подтверждении.
- Все внешние ключи обмена разрешаются; нет дублей компании/месяца; источник для каждого поля известен. Отдельные намеренные дефекты отмечены в сценариях.
- Обязательства, периоды и денежные показатели арифметически согласованы. Нет двойного учета одного платежа как суммы сведений клиента и БКИ.
- Проверены обе стороны порогов суммы, срока, возраста 6/12/24, дней просрочки 29/30/59/60, отношений 0.35/0.50/0.65/0.80 и трендов -0.15/-0.30.
- Функция маршрутизации отдельно проверяется на баллах 29/30/59/60; не все целые баллы достижимы комбинациями текущих вкладов, поэтому это проверки границы функции, не выдуманные опорные компании.
- При финансовом нуле/пропуске нет деления на ноль; отсутствующий ответ не равен отсутствию долгов. Техническая ошибка не дает кредитный отказ.
- Дозапрос сохраняет обе отправки; повтор технической обработки сохраняет одну отправку и два запуска. Двойной submit не дублирует отправку или решение.
- Изменение суммы/срока меняет расчет там, где ожидается; изменение только шага формы не меняет кредитные факты. После правок старый AI-отчет не показывается как актуальный.
- Сотрудник не видит неотправленные правки; клиент не получает чужую заявку, внутренние комментарии или технические fixtures.

Нельзя заявлять accuracy/AUC реального скоринга на метках, которые сформированы нашими же правилами. Здесь измеряем совпадение реализации с политикой, воспроизводимость и качество объяснений.

## 14. Версионирование после demo-0.2

Любое следующее изменение оформляется через таблицу: старое поле/правило → новый смысл → изменение API/данных/ожиданий → затронутые участники. Косметическая подпись не меняет машинный код. Новый обязательный факт или правило требует согласованной версии схемы/набора/политики; следующий такой набор — demo-0.3.

Для demo-0.2 зафиксированы schema_version=2, dataset_version=demo-0.2, policy_version=demo-policy-0.2 и WC_DEMO/version=2. Источник истины — этот файл. В приложение нельзя незаметно загрузить данные 0.1 с пропущенным is_bankrupt и считать их 0.2; импорт проверяет manifest. Старые снимки/оценки сохраняют свою версию. Минимальный C01/C02, importer, черновики и отправка/расчеты уже реализованы под этим контрактом. Начальная миграция — 0001_demo_02; 0002_revision_immutability добавляет защиту отправленных снимков, 0003_document_immutability — метаданных документов, без новых таблиц.

Внешние шаблоны не блокируют реализацию. Реальные клиентские данные и закрытые банковские пороги не становятся частью демо. Изменения по новым материалам принимаются отдельно, а не автоматически.

## 16. Принятые изменения и границы объема

demo-0.2 заменяет первоначальный временный контракт demo-0.1. Приняты четыре уточнения: точные денежные определения без изменения трех числовых полей; отдельное подтверждение демо-проверки БКИ; is_bankrupt в юридическом симуляторе; provenance в существующих JSONB. Формула платежа, балльные пороги, шесть месяцев, восемь опорных профилей и 15 таблиц сохраняются.

Текстовая сводка и фотографии дали терминологические ориентиры, но не реальные веса или пороги. Публичная [справка Маркета](https://yandex.ru/support/marketplace/ru/tools/lending) описывает конкретный продукт; наши правила остаются явно вымышленными. Сырые вложения и внутренние адреса в поставку не переносятся.

Вне текущего хакатон-MVP: 12 месяцев вместо шести, паспортные фото, полноценный KYC/бенефициары/доли, банковский счет и выдача денег, ЭДО/ПЭП, подпись курьером, первоначальный взнос/залог, выбор ставки, календарный день платежа, мобильный канал/МФО, дубли has_email/is_ip, SLA-таймеры и автоистечение заявки. Ничего из этого не планируется добавлять при появлении свободного времени в рамках текущего объема.

Стресс-сценарий со снижением поступлений сохранен только как перспектива развития после хакатона. Кнопки, поля, endpoint, правила, сценарии приемки и отдельная AI-функция для него в demo-0.2 отсутствуют. Действующий AI — тот же навигатор заявки с расчетами backend, сравнением суммы/срока, объяснением и явным fallback.
