# Как работаем с проектом

Статус: рабочие договоренности разработки для согласованного предметного контракта demo-0.2. Формат веток `XX/<имя-ветки>` задан командой; остальные правила ниже предлагаются как рабочий процесс. Рабочий запуск backend описан в BACKEND.md; Docker остается целевым результатом Димы.

## 2. Ветки

Формат: `XX/<короткое-описание-задачи>`.

- `XX` — согласованные латинские инициалы участника, заглавными буквами.
- Описание — на английском, строчными буквами, слова через дефис.
- Если инициалы совпадают, заранее выбираем разные постоянные обозначения.
- Одна ветка соответствует одной задаче, которая вливается через Pull Request (PR).

Примеры: `SB/application-form`, `SB/credit-rules`, `SB/docs-architecture`. Существующая `SB/initial_edits` подходит по общему формату; переименовывать ее ради дефисов не требуется.

`main` содержит согласованную версию проекта. После появления приложения она должна оставаться запускаемой. Отдельную `develop` пока не вводим: короткие ветки и небольшие PR сокращают время интеграции.

## 3. Обычный цикл работы

Перед созданием ветки проверяем незакоммиченные изменения. Не переключаем ветки поверх непонятных локальных правок.

```powershell
git status
git switch main
git pull --ff-only origin main
git switch -c SB/application-form
```

Вместо `SB/application-form` подставляем свои инициалы и задачу. Если работа уже ведется в `SB/initial_edits`, продолжаем ее без повторного создания ветки.

Добавляем в индекс конкретные файлы, просматриваем изменения и делаем небольшой осмысленный коммит. Пример для текущего этапа:

```powershell
git add README.md DEVELOPMENT.md ARCHITECTURE.md IMPLEMENTATION_PLAN.md DATABASE.md USER_FLOWS.md SYNTETIC.md
git diff --cached
git commit -m "docs: describe workflow and proposed architecture"
```

Пока не появились правила исключения локальных файлов, не используем `git add .` и `git add -A`.

Если за время работы изменилась `main`, получаем изменения и вливаем их в свою рабочую ветку:

```powershell
git fetch origin
git merge origin/main
```

Конфликты разбираем по смыслу, затем проверяем результат и завершаем merge. Не выбираем автоматически целиком «нашу» или «чужую» версию.

Публикуем свою ветку и открываем PR в `main`:

```powershell
git push -u origin SB/application-form
```

В PR указываем задачу, результат, способ проверки и ограничения. По возможности другой участник просматривает изменения до вливания. Используем merge commit: небольшие проверенные коммиты остаются видны в истории main. Ветки не удаляем до завершения интеграции.

После вливания обновляем локальную `main`, следующую задачу начинаем в новой ветке. Удалять старую ветку необязательно сразу.

## 4. Коммиты и совместная работа

Формат: `<тип>(<область>): <что изменилось>`. Область необязательна.

| Тип | Назначение |
| --- | --- |
| `feat` | Новая функция |
| `fix` | Исправление ошибки |
| `docs` | Документация |
| `test` | Тесты |
| `refactor` | Изменение устройства кода без изменения поведения |
| `chore` | Зависимости, инструменты и настройки |

Примеры: `feat(applications): add draft saving`, `fix(scoring): handle zero operating surplus`. Описание может быть на русском; внутри команды выбираем единый подход.

- Не коммитим пароли, токены, реальные клиентские сведения, `.env`, `.venv/`, локальные настройки IDE, логи и выгрузки базы.
- После начала реализации добавляем `.gitignore` до первого массового добавления файлов. Правила исключения уже находятся в .gitignore.
- Не переписываем опубликованную историю общей ветки и не применяем force push к `main`.
- Изменения API и схемы базы обсуждаем с теми, кого они затрагивают. Миграции храним в Git; уже примененную общую миграцию исправляем новой миграцией.
- Зависимости добавляем через выбранный менеджер и коммитим соответствующий lock-файл. Вручную lock-файлы не редактируем.
- Изменение запуска сопровождаем обновлением README и этого документа. Текущая ручная приемка — AI_CHECK.md (AI), DOCUMENTS_CHECK.md (документы), BANK_CHECK.md (банк) и SUBMISSION_CHECK.md (клиент/расчеты); малые логически завершенные изменения сохраняем отдельными проверенными коммитами.
- Защита main и автоматические проверки на GitHub пока не настроены; результаты локальной проверки указываем в PR.

## 5. Запуск backend и будущей полной поставки

Backend уже имеет запуск, модели/миграции, авторизацию/импорт, черновики и отправку/расчеты: [проверенные команды и контракты](BACKEND.md). Команды Docker ниже пока целевые: Compose отсутствует.

### Проверка жюри через Docker

Цель — один воспроизводимый запуск всех обязательных компонентов. Предлагаемый интерфейс запуска после реализации:

```powershell
Copy-Item .env.example .env
docker compose up --build
```

Предполагается, что старт сам применит миграции и безопасно добавит демонстрационные данные без дублей. Контракт набора: demo_data/demo_0_2, dataset_version=demo-0.2, schema_version=2, policy_version=demo-policy-0.2, WC_DEMO/version=2. source_version адаптеров: legal-mock-0.2 и bki-mock-0.2. Manifest валидируется перед импортом; случайный старый набор с отсутствующим is_bankrupt не считается валидным 0.2. Минимальные CSV/JSON C01/C02 и команда python -m credit_cabinet.seed уже созданы; CLI проверяет manifest и импортирует одной транзакцией без сброса рабочих данных. Для новых учетных записей в неинтерактивном init нужен секрет DEMO_USER_PASSWORD. Полный набор C01–C08 и Compose добавляются командой отдельно. Для обязательного сценария не потребуются внешние ключи и подписки. Первый запуск может требовать интернет для загрузки образов и зависимостей; после подготовки сборки основной сценарий не должен обращаться к внешним API.

Целевая полная версия дополнительно включает AI-профиль с локальной моделью. Для него предполагается `docker compose --profile ai up --build` с подготовкой весов в отдельном volume. Эта команда также пока не работает: Compose отсутствует. Дима должен проверить полный режим и честно описанный режим без AI, CPU-вариант и GPU-вариант для ноутбука Сергея. Итоговую команду запуска для жюри фиксируем после проверки всей поставки.

Планируемые адреса: веб-интерфейс `http://localhost:8080`, API через `/api`, Swagger через `/docs` на том же адресе. Это целевой контракт, пока не проверенный результат.

Для диагностики и остановки предполагаются стандартные команды Compose:

```powershell
docker compose ps
docker compose logs --tail 100
docker compose down
```

Профили загружаются в PostgreSQL, ответы симуляторов и подготовленные документы находятся в поставке, веса — в volume Ollama. Подтверждения/происхождение сохраняются в существующих снимках; новых таблиц нет. Приемка включает запрет вызовов БКИ/LLM без подтверждения, is_bankrupt=true/null, даты происхождения и прежние численные сценарии.

Данные должны сохраняться в именованных volumes между обычными перезапусками. Команду полного сброса и ее последствия документируем отдельно, когда появятся демонстрационные данные.

### Локальная разработка

Используем Python 3.12, uv, корневые pyproject.toml/uv.lock и src/credit_cabinet. Тесты — tests/, Alembic — migrations/. Установка: uv sync --locked; запуск: uv run python -m credit_cabinet. Подробные настройки, создание учетных записей и проверки — [BACKEND.md](BACKEND.md).

API не применяет миграции и не заполняет данные при старте; Дима добавляет отдельный init. PostgreSQL/роль создаются вне приложения. React/dev proxy выбирает и настраивает Ксюша. Docker останется основным способом независимой проверки полной поставки после его реализации.

С этапа документов актуальна миграция 0003_document_immutability. DOCUMENTS_DIR по умолчанию .data/documents, создается автоматически при первой заявке; каталог исключен из Git. Диме нужен отдельный постоянный записываемый volume с этим путем, без публичной раздачи. Набор DEMO_DATASET_DIR остается в поставке на чтение. Резервирование/перенос должны включать и БД, и копии документов; повторный seed утраченные файлы старых заявок не восстанавливает.

### Что добавим после реализации

- Проверенные версии Python, Docker и Compose, требования к памяти и свободным портам; Node.js — если выбранные инструменты потребуют его.
- Таблицу переменных окружения с назначением и демонстрационными значениями без реальных секретов.
- Команды полного импорта и восстановления демо; запуск backend/миграций уже описан в BACKEND.md.
- Демонстрационные учетные записи клиента и сотрудника банка.
- Сценарии одобрения, отказа, дозапроса, ручного решения и временной ошибки интеграции.

## 6. Готовность задачи и сдача

Задача готова к PR, когда выполнен ее сценарий, проверены затронутые права доступа и ошибки, обновлены контракты и документация. После появления CI обязательные проверки PR должны проходить перед вливанием.

Перед дедлайном проверяем запуск из чистого клона, весь основной сценарий и сохранность данных после перезапуска. Фиксируем SHA сдаваемого коммита; тег добавляем при необходимости. Для приватного репозитория предоставляем жюри доступ к `alfa-hack-2026`, как требует кейс. Эти действия выполняются командой при подготовке сдачи, а не автоматически сейчас.

README к сдаче должен содержать краткий запуск, назначение, архитектуру, окружение и конфигурацию, компоненты и пошаговую проверку. Дополнительно готовим схему состояний и данных, описание API/OpenAPI, коллекцию запросов, синтетические данные, тестовые сценарии и файл `THIRD_PARTY_NOTICES` с моделируемыми интеграциями. Перечень лицензий/интеграций добавим вместе с полной поставкой.

Стресс-сценарий и дополнительные AI-функции не входят в demo-0.2 и не являются задачами этой сборки. Текущая модель объясняет заявку/сравнение суммы и срока; отдельная инфраструктура для будущего стресс-режима не готовится.
