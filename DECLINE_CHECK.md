# Отказ клиента от одобренных условий

Клиент может подписать предложение или нажать красную кнопку **«Отказаться»** рядом с «Подписать документ». Это работает при обычном одобрении и при изменении суммы/срока сотрудником. Отказ сразу закрывает заявку: **APPROVED → REJECTED («Отказано»)**, без подписания. Дополнительного подтверждения нет.

Решение банка, отправленный снимок, расчёты и документы остаются в истории. Отказ клиента не переписывает банковское одобрение: `decision.outcome` остаётся `APPROVED`, а текущий `application.status` становится `REJECTED`. Для определения текущего состояния использовать статус заявки. Клиент и сотрудник видят отдельное пояснение об отказе клиента. Вернуть это предложение к подписанию нельзя; можно создать новую заявку.

## Обновление и запуск

Миграция **0009_client_decline** добавляет nullable JSONB `applications.decline_record`, ограничение REJECTED для заполненной записи, защиту записи от изменения и событие `AGREEMENT_DECLINED`. Новых таблиц, зависимостей, настроек и seed нет. Существующие аккаунты, пароли, заявки, решения и подписи сохраняются.

Локально, из корня проекта с PostgreSQL и настроенным `.env`:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m credit_cabinet
```

`alembic current` и `/health/ready` должны показывать `0009_client_decline`. Во втором терминале:

```powershell
cd frontend
npm run dev
```

Открыть http://localhost:5173. Если npm ещё не добавлен в PATH, из каталога frontend:

```powershell
& 'C:\Users\user\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe' .\node_modules\vite\bin\vite.js
```

Для сервера пересобрать backend и frontend, выполнить штатный одиночный init с `alembic upgrade head` до запуска новой версии API и затем перезапустить сервисы по существующей инструкции [Docker](DOCKER_HANDOFF.md). Сохранить прежние volumes. Сбрасывать БД или пароли не требуется. При сохранённых отказах downgrade ниже 0009 блокируется, чтобы не потерять историю.

## Проверка интерфейса

1. Войти клиентом, открыть **одобренную, ещё не подписанную** заявку. Для проверки использовать отдельную демо-заявку: отказ окончательный.
2. Убедиться, что рядом с «Подписать документ» есть красная **«Отказаться»**.
3. Нажать «Отказаться». Ожидать «Отказано», отметку «Отказ клиента», дату и пояснение о закрытии без подписания. Кнопки подписания и отказа исчезают.
4. Обновить страницу и открыть заявку из «Моих заявок»: результат сохраняется. В истории ровно одно событие отказа клиента. В кредитных договорах профиля компании новый договор не появляется.
5. Войти сотрудником, найти заявку в «Решениях» / фильтре «Отказано», открыть карточку: отказ клиента виден отдельно, прежнее одобрение и предложенные условия сохранены, новых действий сотрудника нет.
6. Повторить на заявке, которую сотрудник одобрил с изменением суммы/срока. После отказа сравнение остаётся для истории и не предлагает подписать условия.
7. На другой заявке проверить обычное подписание: переход в «Подписано» работает; после подписи кнопки отказа нет.

Остановить оба локально запущенных сервера через **Ctrl+C** в каждом терминале.

## Swagger / контракт

`POST /api/applications/{application_id}/agreement/decline`:

```json
{
  "expected_version": 5,
  "decision_id": "UUID решения из decision.id"
}
```

Подставить актуальные `version` и `decision.id` из GET `/api/applications/{id}`. Требуются сессия CLIENT, доступ к компании и обычный `X-CSRF-Token` из GET `/api/auth/csrf`. Дополнительные поля не принимаются.

Ответ 200 — обновлённая заявка с `status=REJECTED`, `signature=null`, пустыми `allowed_actions` и публичным `decline`: `decision_id`, `declined_at`, `declined_by_display_name`. Идентификатор автора остаётся в БД и банковской истории. Аналогичный `decline` есть в банковской карточке.

Неверные версия или решение дают 409 без изменений. Повтор того же отказа после потери ответа возвращает сохранённый результат, не создаёт нового события. Подписанную заявку, черновик или отказ банка отклонить этим запросом нельзя. Отказ и подпись используют одну блокировку заявки: при одновременных запросах выигрывает только один, второй получает 409. Чужая компания — 404; сотрудник вместо клиента или отсутствующий CSRF — 403; без сессии — 401.
