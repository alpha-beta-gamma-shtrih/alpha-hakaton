## Что и где хранится

В PostgreSQL seed добавляет **146 пользователей, 144 компании, 144 membership, 862 финансовые строки и один продукт v3** на пустой базе. На базе с прежними C01/C02 и четырьмя аккаунтами ожидается добавление 142 пользователей, 142 компаний, 142 связей, 850 финансовых строк; продукт добавляется только если его ещё нет.

Ответы источников остаются файлами: 144 ответа ФНС, 145 ответов БКИ с учётом retry C06. Manifest, 18 сценариев и 144 шаблона документов тоже остаются в поставке. При создании заявки backend копирует её документ в приватное хранилище; снимки, проверки, решения и AI-отчёты создаются действиями пользователей. Готовые заявки/решения в seed не подмешиваются.

Действующие профили C01/C02, их финансы, UUID и четыре логина сохранены. Повторный seed не сбрасывает пароли и историю, не меняет финансовые строки пользователя и старые снимки. Серверный банковский признак синхронизируется из sidecar, как предусмотрено demo-0.3. При конфликте существующего профиля seed откатывает транзакцию; базу для обхода ошибки не очищать.

## Обновление на ноутбуке Сергея

Локальная рабочая БД при этой проверке **не заполнялась новым набором**: там сохранены две компании и четыре аккаунта. Проверки импорта выполнены на временных базах/схемах. Для подключения набора:

1. Остановить свой API через Ctrl+C. PostgreSQL оставлять запущенной. Команды выполнять из корня проекта:

   ```powershell
   cd C:\alpha\alpha-hakaton
   .\.venv\Scripts\python.exe -m credit_cabinet.seed --dataset demo_data/demo_0_3 --check-only
   .\.venv\Scripts\python.exe -m alembic upgrade head
   .\.venv\Scripts\python.exe -m credit_cabinet.seed --dataset demo_data/demo_0_3
   ```

2. Проверка выведет `valid=true`, `subset=FULL`, `companies=144`. Миграция остаётся `0005_personal_pricing`; новой миграции для CSV не требуется.
3. Интерактивный seed попросит дважды ввести **новый пароль длиной 12–1024 символа для новых аккаунтов**. Его придумываете вы. Существующие client@example.com, client2@example.com, bank@example.com и bank2@example.com сохранят прежние пароли. Если DEMO_USER_PASSWORD уже задан в окружении/.env, используется он; в Git его не добавлять. Хеширование 142 новых паролей занимает некоторое время.
4. В существующем `.env` должен остаться `DEMO_DATASET_DIR=demo_data/demo_0_3`. URL БД и остальные настройки сохраняются. API и seed должны читать один и тот же набор.
5. Повторить команду seed: все `created` должны стать 0. Изменённые ранее пользователем финансовые строки намеренно сохраняются, поэтому их результаты могут отличаться от эталонных чисел ниже.
6. Запустить backend: `.\.venv\Scripts\python.exe -m credit_cabinet`. React запустить в другом терминале по [FRONTEND_CHECK.md](FRONTEND_CHECK.md). Все прежние кнопки демо-входа работают; новые email вводить вручную. Swagger: http://localhost:8000/docs.

Лимит входа — 10 попыток с одного адреса за 300 секунд, включая успешные. При быстром переборе множества аккаунтов возможен 429: дождаться Retry-After. Ограничение приложения ради нового набора не ослаблялось.

### Через Swagger

1. `GET /api/auth/csrf` → скопировать csrf_token; в `POST /api/auth/login` передать X-CSRF-Token и нужные email/пароль. Для POST/PATCH после входа брать свежий токен тем же GET. Swagger открыт на том же origin; cookie браузер отправляет автоматически.
2. `GET /api/companies` должен вернуть только компанию вошедшего клиента. `GET /api/products` — продукт v3 первым. Их id передать в `POST /api/applications`.
3. `PATCH /api/applications/{id}`: указать expected_version из последнего ответа, requested_amount строкой, term_months числом, purpose_code; в draft_data.confirmations передать data_confirmed=true и credit_history_check_allowed=true. Не подменять финансовые месяцы, если проверяете исходный профиль.
4. `POST /api/applications/{id}/scenarios` с expected_version покажет предварительный маршрут; затем `POST /api/applications/{id}/submit` с актуальной версией и новым UUID submission_key зафиксирует снимок. Сверить статус и assessment с таблицей. reason_codes в API представлены как `assessment.reasons[].code`.
5. Для C04 сохранить отсутствие июня: отправка должна создать дозапрос, а не нулевой месяц. Если UI не даёт отправить неполную форму, этот сценарий проверять через Swagger; неполнота не является ошибкой seed.
6. Для C06 после первого submit войти bank@example.com с прежним паролем; получить `GET /api/bank/applications/{id}` и вызвать `POST /api/bank/applications/{id}/retry-processing` с актуальным expected_version. Ожидается APPROVED, run_no=2, прежний revision_id. Клиентский `/scenarios` попытки не расходует.
7. Проверить download_url документа своей заявки. Под другим клиентом та же ссылка возвращает 404; сотруднику доступен документ отправленной заявки. Прежние заявки продолжают скачивать свои неизменяемые копии.
8. После проверки Ctrl+C в терминалах API/Vite. PostgreSQL и Ollama останавливать не требуется.

```powershell

```

`--check-only` проверяет SHA-256, структуру, ссылки, уникальность, календарь, параметры продукта и содержимое документов относительно seed-финансов. Ожидаемые решения проверяют тесты: все 144 профиля проходят действующий движок, все 18 сценариев — сравнение с эталоном и сквозной API с правами и документами. Отдельный PostgreSQL-тест проверяет расширение заполненной БД, сохранность прежнего снимка/паролей, повторяемость импорта и те же 18 сценариев. Он использует существующий TEST_DATABASE_URL и одноразовую тестовую схему; инфраструктура тестов Димы не менялась.

Диме: каталог не переименован, поэтому Compose продолжает читать `/app/demo_data/demo_0_3`. В новый образ должны попасть все 144 документа и обновлённые JSON/CSV/manifest. Сохранить volumes и выполнить штатный init: Alembic → seed с DEMO_USER_PASSWORD → API. Пароль понадобится и на уже заполненной БД: добавляются новые пользователи. Полная инструкция — [DOCKER_HANDOFF.md](DOCKER_HANDOFF.md). Docker в этой проверке не запускался; его конфигурация не изменялась.
