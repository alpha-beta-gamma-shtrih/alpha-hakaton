## 1. Подготовка и импорт

Команды выполняются из PowerShell в корне проекта. Если старый API работает в твоем терминале, сначала остановить его Ctrl+C.

```powershell
cd C:\alpha\alpha-hakaton
.\.tools\bin\uv.exe sync --locked
.\.venv\Scripts\alembic.exe upgrade head
.\.venv\Scripts\python.exe -m credit_cabinet.seed --check-only
.\.venv\Scripts\python.exe -m credit_cabinet.seed
```

Если uv установлен глобально, вместо .tools/bin/uv.exe используется uv. --check-only проверяет набор без подключения к БД и без секретов; для текущего набора ожидается valid=true, companies=144, subset=FULL; исторический demo_0_2 содержит две компании.

При первом импорте текущего demo_0_3 CLI автоматически использует индивидуальные публичные пароли из [demo_users.json](demo_data/demo_0_3/demo_users.json). Существующие аккаунты сохраняют прежний пароль, UUID, имя, активность и UI-контекст. Старый demo_0_2 без паролей поддерживается через DEMO_USER_PASSWORD или скрытый ввод. Начальная установка — [DEMO_ACCOUNTS.md](DEMO_ACCOUNTS.md).

| Email | Роль | Доступ после импорта |
| --- | --- | --- |
| client@example.com | CLIENT | C01 |
| client2@example.com | CLIENT | C02 |
| bank@example.com | BANK_STAFF | Вход доступен, клиентские API возвращают 403 |
| bank2@example.com | BANK_STAFF | Второй сотрудник для будущих банковских сценариев |

В твоей текущей базе client@example.com уже создан вручную. Его пароль не меняется; индивидуальный пароль из JSON применяется только при создании учётной записи. Число created.users зависит от того, какие email уже существуют.

Повтори ту же команду импорта: все created-счетчики должны стать 0, дополнительного ввода пароля не потребуется. Импорт не создает заявки, не сбрасывает пароли, не перезаписывает финансовые строки и не включает отключенный продукт. Конфликт роли существующего email или условий неизменяемой версии продукта останавливает импорт с откатом всей транзакции.

Для Димы: тот же importer доступен как credit-cabinet-seed после uv sync. Штатный demo_0_3 импортируется без терминала и без DEMO_USER_PASSWORD: пароли входят в demo_users.json. Для старых/собственных наборов без индивидуальных паролей нужен DEMO_USER_PASSWORD либо интерактивный ввод; при его отсутствии неинтерактивный init завершится ошибкой без записи данных. API не запускает seed или миграции автоматически.

## 2. Запуск и вход

```powershell
.\.venv\Scripts\python.exe -m credit_cabinet
```

Открыть http://localhost:8000/docs. Каждая операция: раскрыть блок → Try it out → заполнить поля → Execute. Смотреть Server response.

1. GET /api/auth/csrf → скопировать csrf_token.
2. POST /api/auth/login → вставить его в X-CSRF-Token, указать свой email и пароль кабинета в JSON.
3. GET /api/auth/csrf еще раз → получить уже токен авторизованной сессии.
4. Для POST/PATCH/DELETE использовать именно новый токен. Cookie браузер отправляет автоматически.

GET /api/auth/me должен вернуть CLIENT. Не смешивать localhost и 127.0.0.1: у них разные cookie. Подробнее — [BACKEND.md](BACKEND.md).

## 3. Компания и продукт

GET /api/companies → в items одна компания C01 с названием «ДЕМО — Северный товар». Скопировать ее id как COMPANY_ID. C01 — ключ файла, API принимает UUID, а не строку C01.

GET /api/companies/{company_id} → подставить COMPANY_ID. Ожидаются шесть месяцев апреля–сентября 2026: каждый месяц поступления 1200000.00, выплаты 850000.00, платеж по действующему долгу 30000.00. Суммы в JSON — строки; источник DEMO_PROFILE, credit_history=null.

GET /api/products → один WC_DEMO/version=2. Скопировать id как PRODUCT_ID. Ставка 24.000, сумма 100000.00–5000000.00, сроки 6–24.

Списки компаний, продуктов и заявок имеют общий формат:

```json
{"items":[],"total":0,"limit":20,"offset":0}
```

limit от 1 до 100, offset неотрицательный. Сортировка стабильная; заявки — сначала последние обновленные. В GET /api/applications есть необязательный фильтр company_id, также проверяющий membership.

## 4. Создать черновик

POST /api/applications, текущий X-CSRF-Token и JSON, заменив обе строки на полученные UUID:

```json
{
  "company_id": "COMPANY_ID",
  "product_id": "PRODUCT_ID"
}
```

Ожидается 201. Скопировать id заявки как APPLICATION_ID. В ответе version=1, status=DRAFT, ui_step=NEED, основные параметры null, финансовые месяцы предзаполнены, оба confirmations=false. В allowed_actions EDIT_DRAFT/SUBMIT; отдельная инструкция отправки — SUBMISSION_CHECK.md.

Создание POST не идемпотентно: каждое успешное нажатие создает новый черновик. Ксюша блокирует повторное нажатие на время запроса; после потери ответа сначала проверяет список заявок.

## 5. Сохранить параметры и проверить конфликт

PATCH /api/applications/{application_id}, APPLICATION_ID, текущий X-CSRF-Token:

```json
{
  "expected_version": 1,
  "requested_amount": "1000000.00",
  "term_months": 12,
  "purpose_code": "INVENTORY",
  "purpose_details": "Первая проверка сохранения",
  "ui_step": "FINANCES"
}
```

Ожидается 200, version=2. GET этой заявки должен вернуть те же значения.

Нажать Execute для ТОГО ЖЕ PATCH еще раз, оставив expected_version=1 → 409 VERSION_CONFLICT. Данные не затираются. Для следующей записи получить свежую заявку и передать ее version.

Ксюше: сериализовать автосохранения; после 409 получить GET и показать конфликт, не заменять expected_version автоматически с молчаливой перезаписью чужой правки. Передавать только измененные поля: отсутствующее поле сохраняется, null очищает nullable-поле.

Например, следующий PATCH очищает только пояснение:

```json
{"expected_version":2,"purpose_details":null}
```

Версия станет 3. Контейнеры draft_data/confirmations/financial_months и ui_step очищать через null нельзя.

## 6. Частичные финансы и подтверждения

Использовать актуальную version, ниже пример предполагает 3:

```json
{
  "expected_version": 3,
  "draft_data": {
    "financial_months": [
      {
        "month": "2026-09-01",
        "cash_inflow": "1250000.00",
        "operating_outflow": null,
        "existing_debt_payment": "30000.00"
      }
    ],
    "confirmations": {
      "data_confirmed": true
    }
  }
}
```

Ожидается 200, version=4:

- financial_months содержит ТОЛЬКО сентябрь: массив полностью заменяется, не объединяется с прежними месяцами;
- operating_outflow=null сохраняется как неизвестное значение, не ноль;
- credit_history_check_allowed остается false;
- provenance.financial_months.source становится CLIENT_DECLARED;
- GET компании по-прежнему возвращает шесть исходных месяцев: правка заявки не меняет профиль.

Если нужна обычная форма с шестью месяцами, frontend отправляет весь актуальный массив. Пустой массив [] допустим как неполный черновик. Дубли, месяцы вне апреля–сентября, отрицательные суммы, числа вместо денежных строк и неизвестные поля возвращают 422 без изменения версии/данных.

Можно отдельно сохранить confirmations.credit_history_check_allowed=true; он не превращается в проверку БКИ. Сам PATCH не вызывает источники/LLM, provenance черновика сохраняет credit_history=null. Источники вызываются через submit или подтвержденный scenarios; результаты находятся в assessment/кандидатах. Подтверждения меняются только явными клиентскими полями.

В черновике разрешены положительные сумма/срок вне продуктовых границ для частичного ввода; формат, точность, знак и тип проверяются сразу. Лимиты продукта относятся к будущей отправке. UI получает границы из /products и показывает подсказку. Некорректные значения не округляются автоматически.

## 7. Восстановление после закрытия и перезапуска

1. GET /api/auth/me → ui_context содержит last_application_id и последний сохраненный step.
2. Закрыть/открыть вкладку Swagger и снова получить /me, затем GET заявки по id.
3. Остановить API Ctrl+C в своем PowerShell, запустить той же командой, снова открыть localhost:8000/docs.
4. Пока сессия не истекла, /me и заявка доступны без повторного входа. После истечения войти заново — данные заявки сохраняются.

Сохраняется последняя созданная/отредактированная заявка, не каждый просмотр GET. Идентификатор из UI-контекста повторно проверяется по membership; чужая/недоступная заявка из контекста не возвращается. Успешные создание/PATCH продлевают idle TTL в пределах absolute TTL, GET-чтения его не продлевают.

GET /api/applications выводит сохраненные заявки. GET /api/applications/{id}/events возвращает {"items":[...]} без пагинации и содержит одно событие DRAFT_CREATED. На каждое автосохранение бизнес-событие не создается; технический лог application.draft_saved содержит id/version/request_id.

## 8. Проверить изоляцию клиентов

Сохранить APPLICATION_ID первого клиента.

1. POST /api/auth/logout с текущим CSRF.
2. Получить /csrf и войти как client2@example.com с паролем НОВЫХ аккаунтов, выбранным при seed.
3. GET /api/companies → только C02 «ДЕМО — Южный склад».
4. GET чужой заявки/ее событий и PATCH чужой заявки → 404 APPLICATION_NOT_FOUND.
5. GET чужой компании → 404 COMPANY_NOT_FOUND.
6. Создать свою заявку C02 и проверить, что список содержит только доступные второму клиенту заявки.

Сотрудник банка в этих клиентских маршрутах получает 403 ROLE_FORBIDDEN даже при известном UUID. Банковские очередь/карточка/ручные действия реализованы по BANK_CHECK.md и читают отправленные снимки; технический retry описан также в SUBMISSION_CHECK.md.
