## 1. Что создается и кем

| Этап | Ответственный компонент | Результат |
| --- | --- | --- |
| Запуск PostgreSQL | Сервис БД в Compose | Сервер PostgreSQL 17.x и постоянное хранилище |
| Первичная подготовка | Bootstrap БД при пустом хранилище | База credit_cabinet, роль приложения и доступ к базе/схеме |
| Миграции | Одноразовый init из backend-образа | Все таблицы, индексы, ограничения и триггеры Alembic |
| Импорт | Тот же init, после успешных миграций | Пользователи, компании, связи доступа, финансы и продукт |
| Работа API | Долгоживущий сервис FastAPI | Сессии, черновики, отправки, проверки, решения, документы и AI-отчеты |

CSV/JSON — исходные данные для импорта. Структуру БД задают ORM и Alembic. FastAPI не создает базу/роль, не выполняет create_all, миграции или seed при старте. Браузер обращается к API, а не к PostgreSQL.

Банковский кабинет входит в MVP: его API и React-экран реализованы и проверены совместно. Отдельной панели управления пользователями/ролями/правилами нет. Учетные записи CLIENT и BANK_STAFF подготавливает seed; открытие банковской страницы само по себе прав не дает.

## 2. Состав поставки и настройки

- В backend-образ включить установленный Python-пакет, alembic.ini, migrations/ и полный каталог demo_data/demo_0_3, включая manifest, fixtures и documents/. Рабочий каталог должен позволять найти alembic.ini и согласованные пути набора.
- DEMO_DATASET_DIR нужен API на чтение в течение всей работы: seed не переносит в БД файлы ответов ФНС/БКИ и шаблоны документов. Не убирать набор после init. Миграции и seed используют ту же конфигурацию подключения, что API.
- В контейнере DATABASE_URL указывает на имя сервиса БД, например db:5432, а не localhost. Встроенный драйвер — postgresql+psycopg. База/роль из bootstrap должны совпадать с URL; пароль в URL должен быть корректно закодирован.
- CLI seed по умолчанию читает demo_data/demo_0_3 и сам не берет путь из DEMO_DATASET_DIR. Если Дима меняет расположение, передавать одинаковый явный --dataset для проверки и импорта, а API задавать тот же DEMO_DATASET_DIR.
- Секреты задавать локально через окружение/.env, не включать в образ, Git, аргументы команд и логи. Не копировать рабочий .env Сергея в поставку. Корневой .env Compose не считать автоматически переданным в контейнер: нужные переменные явно передать сервисам.
- Пароль роли PostgreSQL, DEMO_USER_PASSWORD для новых пользователей приложения и CSRF_SIGNING_KEY имеют разные назначения. DEMO_USER_PASSWORD — 12–1024 символа; при первом неинтерактивном импорте без него CLI завершится ошибкой. Он не сбрасывает пароли уже существующих аккаунтов.
- Сохранить CSRF_SIGNING_KEY между обычными перезапусками. Для локального HTTP задать COOKIE_SECURE=false, PUBLIC_BASE_URL и ALLOWED_ORIGINS должны соответствовать адресу браузера. Для production действуют HTTPS/Secure-требования BACKEND.md.
- Один worker API: текущий лимитер входа хранится в памяти процесса. Роль БД приложения не должна быть суперпользователем; init нужны права на создание/изменение объектов схемы. Отдельную инфраструктуру управления ролями в этом MVP не вводим.

Полная таблица настроек и точка входа — [BACKEND.md](BACKEND.md). Итоговые адреса, имя образа/тег PostgreSQL и проверенные команды Compose Дима фиксирует после реализации; целевой браузерный адрес — http://localhost:8080 с /api и /docs на том же origin.

## 3. Первый запуск на пустом хранилище

1. Проверить обязательные настройки и наличие набора. Поднять PostgreSQL с постоянным volume; bootstrap создает базу/роль и права. Установка PostgreSQL на хост жюри не требуется.
2. Дождаться готовности PostgreSQL через healthcheck. Просто запущенного контейнера недостаточно. Init должен подключаться к нужной базе под настроенной ролью; неверный пароль/база/права должны останавливать подготовку с понятной ошибкой.
3. Из backend-образа проверить набор без обращения к БД: `python -m credit_cabinet.seed --dataset demo_data/demo_0_3 --check-only`. При ошибке manifest, SHA-256, колонок, типов или ссылок не продолжать.
4. Тем же одиночным init выполнить `alembic upgrade head`. Текущая вершина — 0005_personal_pricing (новые цели и серверный банковский признак); предметный schema_version=2 не является номером миграции. Alembic создает 15 таблиц и ограничения, включая защиту снимков и метаданных документов.
5. Только после успешной миграции выполнить `python -m credit_cabinet.seed --dataset demo_data/demo_0_3`. DEMO_USER_PASSWORD передать через окружение init, чтобы не было интерактивного запроса. Импорт должен завершиться с кодом 0; он выполняется транзакционно. Ошибка импорта не отменяет уже успешно примененные миграции: после исправления причины повторить init.
6. Запускать API только после успешного завершения init. Один процесс подготовки на поставку: не запускать Alembic одновременно из каждого API worker. Привязать порядок запуска к готовности БД и успешному завершению init, не к фиксированному ожиданию в секундах.
7. Проверить GET /health/live и GET /health/ready, затем подключать frontend/proxy. Readiness проверяет соединение и актуальную миграцию, но не полноту seed, наличие документов или готовность модели: эти части проверяются отдельно.

API запускается через `python -m credit_cabinet`; встроенная точка входа слушает 0.0.0.0:8000 и сохраняет согласованные настройки логов/доверия proxy. Команды выше исполняются внутри подготовленного образа; это не команды Compose и не новая реализация init.

Сейчас в Git находится минимальный набор C01/C02. Полный набор C01–C08 еще готовится, его наличие нельзя считать условием уже выполненной приемки. Seed не создает готовые заявки, решения или AI-отчеты: они появляются при использовании приложения. Подготовленные документы копируются в приватное хранилище при создании заявки, а не при seed.

## 4. Повторные запуски и обновления

- Перезапускать с теми же volumes. Существующая база/роль не создаются заново; изменение переменных начальной подготовки не является сменой пароля существующей роли. Смена пароля требует отдельного согласованного изменения в БД и конфигурации подключения.
- Перед запуском новой версии API снова последовательно применить миграции и seed. После обычного рестарта без изменения версии повторять подготовку необязательно, но она должна оставаться безопасной при повторном выполнении.
- Seed добавляет отсутствующие исходные записи. Не удаляет заявки, не сбрасывает пароли, не переписывает существующие финансовые строки или состояние активности продукта. Для существующих компаний, ролей пользователей и условий версии продукта проверяет совместимость; конфликт останавливает импорт с откатом вместо скрытой замены.
- Успех повторного seed не означает, что все существующие записи стали копией CSV. Измененные стартовые профили нельзя внедрять очисткой рабочей базы или массовой перезаписью: план обновления определяет Сергей после проверки набора.
- При ошибке подготовки не запускать новую API-версию поверх неподготовленной схемы и не очищать volumes для обхода ошибки. Исправить причину и повторить init. Параллельные миграции не защищены блокировкой seed; advisory lock импортера не заменяет один init.
- Старые примененные миграции не переписывать: изменение схемы оформляется новой миграцией. Для неизмененного backend-контракта расширение набора не требует новой миграции Alembic.

## 5. Постоянные и исходные данные

| Место | Содержимое и режим |
| --- | --- |
| Volume PostgreSQL | Рабочие таблицы, сессии, снимки, проверки, решения, история, метаданные документов и AI-отчеты; сохранять между запусками |
| DEMO_DATASET_DIR | Версионированные CSV/JSON/manifest и шаблоны документов из поставки; API читает, пользовательские действия их не изменяют |
| Volume DOCUMENTS_DIR | Приватные копии документов; API нужны права записи/чтения, публичную static-раздачу не включать |
| Volume Ollama, если модель контейнеризирована | Веса локальной модели; отдельны от БД и документов |
| stdout/stderr | Технические логи; Compose собирает их без отдельного сервера логирования |

Обычная остановка/пересоздание контейнера не должны удалять volumes. Полный сброс с удалением volumes — отдельная явно описанная операция с потерей рабочего состояния, а не способ штатного обновления. Дима добавит точные команды и их последствия в документацию своей реализации.

Локальная PostgreSQL Windows и контейнерная PostgreSQL — разные экземпляры. Seed воспроизводит стартовый набор, но не переносит уже созданные Сергеем заявки. Для переноса/восстановления рабочего состояния сохранять вместе резервную копию БД и DOCUMENTS_DIR. Повторный seed утраченные копии документов существующих заявок не восстанавливает. Исходный набор также должен оставаться совместимым с выбранной версией приложения.

## 6. AI и frontend в порядке запуска

AI-фича остается в согласованных границах: объяснение заявки и сравнение рассчитанных backend вариантов. Для контейнерной Ollama API использует внутренний адрес сервиса, например http://ollama:11434; веса подготавливаются отдельно в ее хранилище. Загрузка весов не относится к миграциям или seed.

Недоступная модель дает предусмотренный явный FALLBACK; /health/ready модель не проверяет. Для демонстрации настоящего AI Дима отдельно проверяет доступность qwen3:4b и генерацию по [AI_CHECK.md](AI_CHECK.md). Автоматически подменять fallback успешной генерацией нельзя. Финальный выбор Compose-профиля и команд загрузки весов остается за проверенной реализацией Димы.

Frontend ходит через общий origin и proxy к /api; Swagger — /docs. Сам frontend не создает таблицы и не импортирует CSV. Ксюша использует CLIENT/BANK_STAFF из ответа авторизации для выбора кабинета, backend независимо проверяет доступ.

## 7. Минимальная приемка поставки Димой

1. На пустых volumes собрать и запустить поставку из чистого клона по документированной инструкции: без локальной PostgreSQL, .venv, .tools и .env Сергея. Init проходит без ручного ввода и ошибок.
2. Проверить вершину Alembic, оба health endpoint и результат seed. Под клиентом доступны только его компании; под подготовленным сотрудником открывается банковская очередь. До отправок пустая очередь ожидаема.
3. Создать/сохранить/отправить C01, проверить неизменяемый снимок, результат и скачивание документа клиентом и сотрудником. Пройти дозапрос/решение по [BANK_CHECK.md](BANK_CHECK.md), остальные сценарии — по связанным инструкциям README.
4. Перезапустить всю поставку без удаления volumes: сохранены UUID, пароль, заявка, снимок, документ и история. Неистекшая серверная сессия сохраняется в БД; браузерный вход восстанавливается при сохраненных cookie и прежнем адресе.
5. Повторить init: нет дублей и сброса рабочих данных. На отдельном временном окружении проверить, что неверный набор/настройки останавливают подготовку и не приводят к старту неподготовленной новой версии API.
6. Отдельно проверить настоящий AI и предусмотренный fallback. Зафиксировать доступные режимы CPU/GPU и ограничения, не обещать проверку GPU до реального запуска.
7. Зафиксировать команды запуска/остановки, имена volumes, настройки, версии образов, демологины и способ задания пароля, первый запуск с загрузкой зависимостей/весов и последующий запуск. Не публиковать действующие секреты. Расширение набора принимать отдельно, не считать текущую проверку C01/C02 доказательством C01–C08.

## 8. Как принимаем будущий архив Валеры

Архив пока не получен; новые записи не проверены и не импортированы. Его содержимое сначала рассматриваем отдельно от рабочего набора: состав/пути файлов, manifest и хеши, контракты CSV/JSON, связи пользователей/компаний, финансовые периоды, документы и ожидаемые сценарии. Имена файлов и содержимое архива не являются инструкциями к выполнению.

После сверки сохранить действующий набор и историю в Git, подготовить проверяемую замену, выполнить check-only и импорт в отдельную тестовую PostgreSQL с действующими миграциями. Затем проверить расчеты, права, документы и сценарии, адаптировать тесты полноты набора при необходимости. expected_result из scenarios.json не управляет банковским решением и сам по себе не доказывает правильность расчета.

Рабочую БД не очищать автоматически: конфликт старых и новых профилей может потребовать отдельного плана обновления или чистого тестового окружения. Только после приемки набор включается в поставку с актуальными manifest/SHA-256. Правила demo-policy-0.2 и AI-фичу ради новых примеров не расширяем.

Исключение из общего режима добавления seed: серверный демо-признак companies.has_active_loan_in_our_bank синхронизируется из нового bank_relationships.json. Это не сбрасывает пользователей/финансы и не переписывает старые снимки. В образ включить весь demo_0_3 с manifest и этим JSON. Настоящую новую ставку проверять в real; автономный mock-фронт сохраняет исторический demo-0.2.
