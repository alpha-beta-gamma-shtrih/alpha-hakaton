# Сохранённые варианты финансирования

Исправление от 25 октября 2026 года. Ветка `SB/fixed-financing-options`. Меняется хранение и переключение вариантов; политика demo-0.3, ставки, синтетика, модель и prompt ИИ остаются прежними. Приоритет пользователя и новое поведение AI будут отдельным следующим изменением после приёмки этой ветки.

## Поведение

Первый набор строится от сохранённой суммы и срока: исходный запрос, 80% суммы с прежним сроком, исходная сумма со сроком +12 месяцев. Учитываются минимум суммы и максимум срока продукта; дубли удаляются. Поэтому допустимы один или два варианта вместо трёх. Это условия одного WC_DEMO, а не разные кредитные продукты.

Набор и выбранная карточка сохраняются в PostgreSQL. Выбор меняет сумму/срок заявки, но не её исходную карточку и не остальные предложения. Все разницы считаются относительно «Исходного запроса». На каждой карточке есть кнопка выбора, включая возврат к исходной; активная отмечается «Выбран». Калькулятор и форма показывают выбранные условия. Перезагрузка страницы, выход и повторный вход сохраняют набор и выбор.

| Изменение | Что происходит |
| --- | --- |
| Выбор существующей карточки | Те же id набора и условия карточек; меняются выбранная карточка, сумма/срок заявки и её версия |
| Повторный выбор уже активной карточки | Ничего не меняется, версия не увеличивается |
| Ручная правка суммы или срока | Набор становится неактуальным, даже при возврате прежних чисел; карточки не пересоздаются |
| Правка финансов, цели, партнёра, согласия БКИ, данных компании/банка/продукта или источников | Сравнение больше не считается актуальным; для применения нужен пересчёт |
| Переход между шагами, пояснение цели, подтверждение корректности данных | Само по себе не меняет расчёт и не пересоздаёт набор |
| «Обновить варианты» | Явно создаётся новый набор от текущих сохранённых суммы/срока; его исходный запрос выбран по умолчанию |
| Отзыв согласия БКИ | Предыдущие карточки с кредитными расчётами скрываются; без согласия можно явно построить только ориентировочный набор |
| Отправка заявки | Снимок получает выбранные сумму/срок; менять условия отправленной заявки через карточки нельзя |

Неактуальные карточки остаются для сравнения с пометкой, но без зелёного маршрута и возможности применения. Изменившиеся исходные сведения нельзя выдавать за прежнее персональное предложение. «Обновить варианты» доступно после завершения сохранения и при корректных параметрах продукта.

## Обновление и запуск

Остановить свои API/Vite через Ctrl+C. PostgreSQL и Ollama не останавливать, рабочую `.env` и volumes не удалять.

```powershell
cd C:\alpha\alpha-hakaton
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m credit_cabinet
```

Ожидаемая вершина — **0006_scenario_sets**. Миграция добавляет nullable JSONB-поле `applications.scenario_set`; на SQLite в тестах это JSON. Таблиц остаётся 15. Пароли, компании, финансы, отправки и их снимки сохраняются. На локальной БД Сергея миграция уже применена при этой доработке: 146 аккаунтов, 144 компании и 8 заявок сохранены; пароли и содержимое прежних снимков проверены до/после обновления. Перезапуск seed для этой фичи не нужен. У прежних заявок набора нет; он появится при первом открытии готового черновика.

Во втором терминале:

```powershell
cd C:\alpha\alpha-hakaton\frontend
npm run dev
```

Если npm отсутствует в PATH, прежняя команда для этого ноутбука:

```powershell
& 'C:\Users\user\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe' .\node_modules\vite\bin\vite.js
```

Открыть http://localhost:5173. Использовать real-режим и прежний пароль client@example.com. Локальная миграция и состояние рабочей БД при передаче уточняются в итоговом ответе; команда upgrade безопасна при повторе.

Для Docker пересобрать образы и выполнить штатный запуск Димы с сохранением volumes: init должен применить Alembic до API. В контейнере `alembic current` и `/health/ready` должны показывать 0006_scenario_sets. Compose, загрузка модели и данные seed этой фичей не меняются. При обычном обновлении не использовать удаление volumes.

## Проверка через React

1. Создать новую заявку C01. Выбрать «Закупка товара или материалов», 2 600 000 ₽, 20 месяцев. Включить демо-проверку истории, дождаться сохранения. Если набор успел появиться без согласия, нажать «Обновить варианты», чтобы получить персональные расчёты.
2. Убедиться, что показаны: «Исходный запрос» 2 600 000 / 20, «Меньше сумма» 2 080 000 / 20, «Дольше срок» 2 600 000 / 32. При неизменённой C01 ставки составляют 20%, 20%, 21% соответственно: длинный срок учитывает действующую надбавку, а не копирует ставку исходной карточки.
3. Выбрать меньшую сумму. В форме должно стать 2 080 000 / 20; исходная карточка останется 2 600 000 / 20, а третья — 2 600 000 / 32. Новых 1 664 000 ₽ появиться не должно.
4. Выбрать больший срок: форма 2 600 000 / 32. Вернуться к исходному: форма 2 600 000 / 20. Повторить цикл несколько раз — условия трёх карточек остаются прежними, отметка «Выбран» перемещается.
5. Выбрать меньшую сумму и перезагрузить страницу. Выбранная сумма и все три карточки должны восстановиться. Можно выйти и войти тем же аккаунтом — набор тоже сохранится.
6. Вручную ввести 3 000 000 ₽, дождаться сохранения. Старые карточки остаются, но появляется сообщение о неактуальности, кнопки выбора выключены. Нажать «Обновить варианты» один раз: новый набор должен начинаться с 3 000 000 / 20 и содержать 2 400 000 / 20 и 3 000 000 / 32.
7. Изменить цель или партнёрский признак. Проверить предупреждение и явное обновление. При отзыве согласия БКИ прежние кредитные расчёты должны скрыться сразу, включая время автосохранения.
8. Проверить границы: 100 000 ₽ / 60 месяцев даёт одну карточку, без дублирующихся альтернатив. При сроке 59 месяцев длинный вариант — 60, а не 71; подпись «Дольше срок» соответствует фактическим условиям.
9. Открыть одну заявку в двух вкладках. Выбрать вариант в первой; попытка записать старую версию во второй должна закончиться конфликтом с предложением загрузить актуальную заявку, без тихой перезаписи выбора.
10. После подтверждения шага «Потребность» выбор блокируется существующей логикой фронта. Для смены условий нажать «Редактировать» на этом шаге. Это не изменяет набор, только разрешает редактирование формы.
11. При отправке проверить выбранные сумму/срок в неизменяемом снимке и в карточке сотрудника. Прежние отправки не меняются. Обычное сохранение формы не заменено отправкой.

Существующее AI-сравнение теперь читает те же сохранённые варианты. Его модель, формат текста и приоритет пользователя в этой ветке не дорабатываются. После явного обновления набора старый сравнительный отчёт становится неактуальным, даже если текущие сумма и срок не изменились. Обычный разбор EXPLAIN и текущий калькулятор относятся к выбранным условиям.

## Контракт Swagger

Все маршруты доступны клиенту только для своих заявок; банк получает 403, другой клиент/архивная заявка — 404. Изменяющие запросы требуют cookie, CSRF и допустимого Origin, как существующие API. Новые поля нельзя подставить через обычный PATCH черновика.

| Метод и путь | Назначение |
| --- | --- |
| GET `/api/applications/{id}/scenario-set` | Прочитать набор или null; ничего не создаёт и не повышает версию |
| POST `/api/applications/{id}/scenario-set` | Создать первый набор; существующий вернуть без изменения. Тело: expected_version, refresh=false |
| POST `/api/applications/{id}/scenario-set` с refresh=true | Явно заменить набор новым от текущих условий |
| POST `/api/applications/{id}/scenario-set/select` | Выбрать существующую карточку; тело: expected_version, scenario_set_id, candidate_id |
| POST `/api/applications/{id}/scenarios` | Прежний текущий калькулятор; продолжает считать выбранные условия, не сохраняет предложения |

POST создания/обновления/выбора возвращает `{application, scenario_set}`. После операции брать новую версию из `application.version`. candidate_id — REQUESTED, LOWER_AMOUNT или LONGER_TERM; возвращённые набором идентификаторы являются единственными доступными вариантами. Ответ набора содержит id, created_at, application_version, selected_candidate_id, mode, candidates, is_current и stale_reason.

Пример выбора:

```json
{
  "expected_version": 5,
  "scenario_set_id": "UUID из ответа создания набора",
  "candidate_id": "LOWER_AMOUNT"
}
```

UUID и expected_version в примере заменить фактическими. Сохранённые кандидаты не присылаются клиентом и не пересчитываются от выбранной суммы. Создание и выбор повышают версию только при изменении. Старый expected_version → 409 VERSION_CONFLICT; заменённый id набора → 409 SCENARIO_SET_CONFLICT; устаревшие данные → 409 SCENARIO_SET_STALE; отсутствующий вариант → 422 SCENARIO_NOT_FOUND. Для отправленных заявок изменение запрещено.
