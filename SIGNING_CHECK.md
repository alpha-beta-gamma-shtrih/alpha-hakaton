# Проверка демонстрационного подписания

Если сотрудник одобрил изменённые сумму/срок, документ содержит эти итоговые условия из Decision. Клиент перед подписанием видит предупреждение и сравнение в карточке. Отдельный сценарий — [BANK_OFFERS_CHECK.md](BANK_OFFERS_CHECK.md).

После одобрения заявка проходит APPROVED → SIGNED («Подписано»). Клиент видит финальные условия, подтверждает их кнопкой, попадает в «Мои заявки». Это эмуляция электронной подписи для хакатона: юридически значимая ЭП, договор с реальным банком и выдача средств не создаются. Дополнительная регистрация, SMS, загрузка сертификата и внешнее ЭДО не нужны.

## 1. Обновление и запуск

Из корня проекта, с настроенным `.env` и работающей PostgreSQL:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m credit_cabinet
```

Вершина — **0008_bank_offers**. Существующие учётные записи, пароли, сессии и заявки сохраняются. Для этой фичи seed не требуется. У каждого участника своя БД, поэтому миграцию нужно применить и на его машине. GET http://localhost:8000/health/ready должен вернуть 200 и schema_revision=0008_bank_offers.

Во втором терминале из корня:

```powershell
cd frontend
npm run dev
```

Открыть http://localhost:5173. Если npm отсутствует в PATH на ноутбуке Сергея, зависимости уже установлены и Vite можно запустить так из корня:

```powershell
cd frontend
& 'C:\Users\user\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe' .\node_modules\vite\bin\vite.js
```

Использовать режим real: стандартный запуск обращается к FastAPI через proxy. Полная подготовка окружения — [FRONTEND_CHECK.md](FRONTEND_CHECK.md). Процессы завершаются Ctrl+C каждый в своём терминале.

Для Docker: пересобрать API и web, выполнить штатный одиночный init с `alembic upgrade head`, затем запускать API/web на прежних volumes. Не удалять базу, не запускать `down -v`, не сбрасывать данные ради миграции. Имеющийся seed init может выполниться штатно, но подписей он не генерирует. Новых зависимостей, переменных окружения и volumes нет.

## 2. Проверка через React

1. Войти клиентом C01 (`client@example.com`) с ранее заданным паролем. В «Обзоре» в блоке «Как проходит заявка» все цифры 1–4 красные.
2. Открыть свою уже одобренную заявку либо создать новую на 1 000 000 ₽, 12 месяцев, цель «Иное», пройти шаги, отметить подтверждения и отправить. Для исходного C01 ожидается одобрение. При других финансовых данных использовать фактически одобренную заявку; подписание доступно после автоматического и ручного одобрения.
3. В карточке APPROVED нажать **«Подписать документ»**. В форме видны компания/ИНН/цель, одобренные сумма/срок/ставка/платёж, расчётные общая сумма выплат и переплата. Проверить совпадение с решением. Суммы на карточках округлены до рублей, backend сохраняет копейки.
4. В форме явно указана эмуляция подписи. Кнопки скачивания этого документа нет. Нажать **«Закрыть»**: статус остаётся «Одобрено», записи о подписи не появляется.
5. Снова открыть форму, при необходимости прокрутить вниз и нажать **«Подписать»**. Во время запроса кнопка показывает загрузку; повторное нажатие и закрытие заблокированы. При ошибке форма остаётся открытой с сообщением.
6. После успеха форма закрывается, открываются **«Мои заявки»**, строка имеет статус **«Подписано»**. Обновить страницу: статус сохраняется. Заявка находится и во вкладке «Завершённые».
7. Открыть заявку. Видны дата и имя участника, в истории — событие демо-подписания. **«Посмотреть подписанные условия»** открывает прежний документ для чтения, без повторной кнопки подписи. Редактирование, повторная отправка и удаление недоступны.
8. Войти сотрудником банка. В «Решениях» включить фильтр «Подписано», открыть эту заявку. Видны одобренное решение, статус, дата и имя подписавшего. Новое решение/дозапрос и подпись за клиента недоступны.
9. В черновике, при отказе, дозапросе и ручном рассмотрении кнопки подписи нет. Другой клиент без membership компании не видит ни заявку, ни документ.

Подготовленные CSV в отдельном блоке «Документы заявки» по-прежнему скачиваются по прежним правилам. Запрет выгрузки относится к форме демонстрационного договора.

## 3. Контракт API и Swagger

Swagger: http://localhost:8000/docs, группа **agreements**. Войти клиентом обычным способом: GET `/api/auth/csrf`, POST `/api/auth/login` с X-CSRF-Token, затем снова GET `/api/auth/csrf` для токена сессии. Cookie браузер хранит сам; после смены аккаунта получить новый CSRF. Для React эти действия выполняет API-клиент.

1. GET `/api/applications/{id}` возвращает свежую `version`. В APPROVED `allowed_actions` содержит `SIGN_AGREEMENT`.
2. GET `/api/applications/{id}/agreement` возвращает `{content, content_sha256, signature}`. До подписи signature=null. Content содержит финальные условия и decision_id, а также revision_id, компанию, цель, дату решения, версию шаблона и демонстрационную оговорку. GET не меняет статус/версию и не требует CSRF.
3. POST `/api/applications/{id}/agreement/sign` с текущим X-CSRF-Token и допустимым Origin; тело взять из фактически просмотренного документа:

```json
{
  "expected_version": 7,
  "decision_id": "UUID из content.decision_id",
  "content_sha256": "64 символа из content_sha256",
  "accepted": true
}
```

Число 7 — пример, заменить на свою version; строковые подсказки также заменить на реальные значения. Ответ 200 — актуальная заявка со status=SIGNED, пустыми allowed_actions и signature. В signature: decision_id, content_sha256, signed_at, signed_by_display_name и method=DEMO. Дальнейший GET agreement возвращает сохранённый документ и ту же подпись.

| Проверка | Ожидание |
| --- | --- |
| accepted=false / отсутствует / строка вместо bool | 422, подпись не создаётся |
| Нет сессии / роль BANK_STAFF | 401 / 403 |
| Другая компания без membership | 404 |
| Нет CSRF или запрещённый Origin у POST | 403 |
| Не APPROVED и не SIGNED | 409 AGREEMENT_NOT_AVAILABLE |
| Устаревшая version до первой подписи | 409 VERSION_CONFLICT |
| Другие decision_id или SHA-256 | 409 AGREEMENT_CHANGED |
| Идентичный повтор после успеха, даже с прежней version | 200 с исходной подписью; второго события нет |
| Одновременные одинаковые запросы | Одна подпись и одно событие; повтор получает сохранённый результат |

Backend не принимает сумму, ставку, дату или автора подписи от браузера. Свободное PATCH-поле signing_record запрещено. Подписывать может любой уполномоченный CLIENT с membership компании — это существующее упрощение профиля компании для MVP, отдельной роли подписанта нет.

## 4. Хранение и границы

В `applications.signing_record` (nullable JSONB) записываются полный документ, SHA-256, decision_id, signed_by_user_id, имя участника на момент подписи, серверный signed_at и method=DEMO. Все 15 предметных таблиц остаются прежними. Поле заполняется только при SIGNED; триггер запрещает его дальнейшее изменение. В API внутренний user_id подписи не возвращается. Текущая схема не заявляется промышленным криптографическим аудитом.

Документ формируется из финального Decision и связанного неизменяемого ApplicationRevision. Подписание не пересчитывает кредит и не создаёт новую отправку/оценку/решение. `closed_at` сохраняет время банковского решения, время подписи хранится отдельно. Статус, запись подписи и событие AGREEMENT_SIGNED с автором фиксируются одной транзакцией под блокировкой заявки. Сохраняется счётчик версии; последовательный или параллельный повтор не дублирует событие.

При перезапуске данные читаются из PostgreSQL. Изменение текущего каталога/финансов компании не переписывает подписанный документ. Откат миграции при существующих подписях намеренно остановится: нельзя незаметно удалить сохранённые записи. Нормальный путь обновления — `upgrade head` с сохранением volumes.

Локальные frontend mock поддерживают тот же путь для изолированной проверки UI; в рабочем режиме это не замена записи в PostgreSQL. Реальная ЭП, проверка полномочий подписанта, подписание PDF, ЭДО и выдача денег остаются за пределами этой реализации.
