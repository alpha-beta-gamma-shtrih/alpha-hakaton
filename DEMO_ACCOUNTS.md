# Учётные записи для проверки приложения

Все логины и индивидуальные пароли находятся в одном файле: **[demo_data/demo_0_3/demo_users.json](demo_data/demo_0_3/demo_users.json)**. У каждой записи `email` — логин, `password` — пароль, `role` — роль. Это опубликованные тестовые доступы к вымышленным данным.

В файле 146 аккаунтов: 144 клиента и два сотрудника банка. Пароли случайные, разные у всех; для C01, C02 и обоих сотрудников подготовлены новые значения, отдельно от прежних локальных доступов Сергея.

## Первый запуск в Docker или на новом сервере

1. Установить и запустить Docker Engine с Compose. На Windows запустить Docker Desktop.
2. В корне репозитория создать `.env` из `.env.example`, если его ещё нет. Задать собственные `POSTGRES_PASSWORD` и `CSRF_SIGNING_KEY` (от 32 символов), адрес сайта и `ALLOWED_ORIGINS`. Для HTTPS включить `COOKIE_SECURE=true`. Это настройки инфраструктуры; пароли пользователей в `.env` задавать не нужно. Для локальной проверки адрес уже настроен на `http://localhost:8080`.
3. Оставить `DEMO_DATASET_DIR=demo_data/demo_0_3`. `DEMO_USER_PASSWORD` можно оставить пустым: у полного набора есть индивидуальные пароли.
4. Из корня запустить `./start.sh` (Linux) или `.\start.ps1` (PowerShell). Скрипт собирает образы, запускает тесты в отдельной тестовой БД и поднимает приложение. На первом запуске загружаются образы и веса модели.
5. Init автоматически применит `alembic upgrade head`, затем seed. На пустой БД появятся 146 пользователей, 144 компании, 862 финансовые строки, 144 membership и один продукт. В БД сохраняются только Argon2id-хеши паролей. Backend стартует после успешного init.
6. Открыть `http://localhost:8080` (либо настроенный адрес сервера), открыть указанный JSON и скопировать `email` и `password` выбранной учётки. Кнопки демо-аккаунтов выбирают email; пароль вводится вручную. Создавать аккаунты через Swagger не требуется.

Проверить C01, C02 и обоих сотрудников: после каждого входа выйти из аккаунта перед следующим. Клиент видит свою компанию, сотрудник — банковскую очередь. Готовые заявки seed не создаёт; создать и отправить заявку можно из клиентского кабинета.

`docker compose logs init` показывает результат импорта без паролей. Остановка — `docker compose stop`; повторный запуск — `docker compose up -d frontend`. Volumes и учётные записи сохраняются.

## Уже существующая БД

Импорт добавляет отсутствующие email и сохраняет UUID, пароли, активность и данные существующих пользователей. Повторный init не меняет их хеши. Поэтому **на прежней локальной БД действуют прежние пароли**, даже если в JSON указаны новые. Новый сервер с пустой БД и новая установка проверяющих получают доступы из JSON.

Изменение поля `password` в файле не сбрасывает пароль существующей учётки. Не удалять рабочую БД или volume ради смены паролей. Для проверки чистой установки использовать отдельное окружение/Compose project со своим `.env`, свободным `FRONTEND_PORT` и новыми volumes.

Для старого `demo_0_2` или собственного набора без поля `password` сохранён запасной способ: `DEMO_USER_PASSWORD` длиной 12–1024 символа либо скрытый интерактивный ввод. Если у нового пользователя поле есть, оно имеет приоритет над общим паролем. При недостающем пароле неинтерактивный импорт завершится ошибкой без частичного создания данных. После ручной правки JSON обновляется его SHA-256 в `manifest.json`; `--check-only` проверяет целостность до подключения к БД.

Эти доступы намеренно общедоступны для демо. Их не использовать для реальных клиентских данных. Личные секреты, пароль роли PostgreSQL и CSRF-ключ по-прежнему остаются вне Git. Пароли из seed не выдаются API и не включаются в mock-данные frontend.
