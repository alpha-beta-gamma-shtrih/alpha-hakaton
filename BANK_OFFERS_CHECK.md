# Одобрение с изменением условий: проверка

Сотрудник в MANUAL_REVIEW может одобрить исходный запрос либо предложить меньшую сумму и другой срок. Ставку, платёж, переплату, нагрузку и оценку нового предложения считает backend. Исходная отправка и её оценка сохраняются. Клиент получает APPROVED с пометкой об изменении условий и принимает предложение существующей демо-подписью → SIGNED.

## 1. Обновление и запуск

Миграция **0008_bank_offers** добавляет nullable JSONB `decisions.offer_snapshot`; предметных таблиц по-прежнему 15. На старых решениях поле пустое. Seed, новые пароли, переменные окружения и зависимости не требуются.

Из корня проекта с настроенным `.env` и работающей PostgreSQL:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m credit_cabinet
```

`alembic current` и GET http://localhost:8000/health/ready должны показывать 0008_bank_offers. В другом терминале:

```powershell
cd frontend
npm run dev
```

Если на ноутбуке Сергея npm отсутствует в PATH, вместо `npm run dev` из frontend:

```powershell
& 'C:\Users\user\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe' .\node_modules\vite\bin\vite.js
```

Открыть http://localhost:5173. Cookie и CSRF React обрабатывает самостоятельно. Полная подготовка — [FRONTEND_CHECK.md](FRONTEND_CHECK.md). Остановка — Ctrl+C в каждом терминале.

Для Димы: пересобрать API и web, выполнить штатный одиночный init (`alembic upgrade head`) перед API на прежних volumes. Базу не пересоздавать, `down -v` не использовать. Стандартный идемпотентный seed init допустим; эта фича не требует нового импорта. Откат 0008 при существующих offer_snapshot намеренно запрещён, чтобы не потерять предложения.

## 2. Основной сценарий через интерфейс

Пример относится к исходному профилю C01 и продукту v3. Если финансовые данные своей заявки уже изменяли, создать отдельную новую заявку с исходными финансами профиля.

1. Войти клиентом `client@example.com` со своим паролем. Создать заявку: **2 500 000 ₽, 12 месяцев, «Иное»**, партнёрская покупка выключена. Пройти шаги, отметить подтверждения и отправить. Ожидается MANUAL_REVIEW: ставка 20%, платёж 231 586,26 ₽, нагрузка около 74,74%, риск-балл сотрудника 40. Клиент балла не видит.
2. Войти `bank@example.com`, открыть заявку в очереди. Доступны обычное одобрение, отказ, дозапрос и **«Одобрить с изменением условий»**.
3. Открыть новую форму. Исходные значения предзаполнены, расчёт недоступен до изменения суммы или срока. Сумма ограничена минимумом продукта и исходным запросом; срок — версией продукта (v3: 6–60 месяцев, v2: 6–24).
4. Ввести **1 500 000 ₽, 36 месяцев**, нажать **«Рассчитать условия»**. Ожидается ставка **21,500%**, платёж **56 898,41 ₽**, сумма выплат **2 048 342,76 ₽**, переплата **548 342,76 ₽**, нагрузка около **24,83%**, риск-балл 0. Экран округляет основные суммы до рублей.
5. Проверить таблицу «Запрос клиента → Предложение банка» и разложение ставки. Отредактировать срок: предыдущий расчёт исчезает, подтверждение сбрасывается. Снова поставить 36 и рассчитать. Простое открытие/изменение формы и расчёт не сохраняют решения.
6. Нажать «Отмена» и открыть форму снова: заявка всё ещё в ручном рассмотрении. Повторить расчёт, заполнить обоснование минимум 20 символов, при необходимости внутренний комментарий, отметить подтверждение и нажать **«Одобрить на этих условиях»**.
7. В карточке банка остаются исходные 2,5 млн / 12 месяцев и исходная оценка; отдельно видны итоговое предложение и его риск-балл. Действий нового решения больше нет. В «Решениях» сумма/срок отображаются по одобренному предложению; риск при пометке «Исходная оценка» относится к исходному запросу.
8. Войти клиентом. Обзор и «Мои заявки» показывают **1,5 млн ₽, 3 года**, пометку изменения банком. В карточке — «Одобрено на изменённых условиях», новое обоснование, сравнение и ставка. Старый расчёт явно обозначен как расчёт исходного запроса. Риск-баллов и внутренних комментариев нет.
9. Нажать **«Подписать документ»**. Форма показывает **1,5 млн ₽ / 36 месяцев / 21,5%** и новый платёж, предупреждает об изменении условий. «Закрыть» ничего не принимает. «Подписать» фиксирует эти условия, открывает «Мои заявки» со статусом SIGNED. Перезагрузить страницу и повторно открыть документ: условия прежние. Подпись демонстрационная, средства не выдаются.

## 3. Ограничения и конфликты

- Нельзя увеличить сумму сверх запроса, выйти за границы продукта, вручную задать ставку, изменить цель или финансовые данные за клиента. Неизменённые параметры требуют обычного одобрения.
- Для исходного C01 попробовать 2,5 млн ₽ на 6 месяцев: нагрузка превышает 80%, расчёт виден, но подтверждение и одобрение недоступны. Backend также запретит такой POST decision.
- Недоступный источник, неизвестное банкротство, жёсткий отказ, незавершённая обработка и отсутствие разрешённого ручного одобрения не обходятся новой кнопкой. Возможность расчёта использует существующее allowed_actions=APPROVE.
- При двух сотрудниках на одной версии одно решение проходит, второе получает 409. Изменённая версия/параметры/контекст требуют нового расчёта. Двойное решение по уже завершённой заявке запрещено.
- Разрешён результат нового расчёта APPROVE либо MANUAL_REVIEW/BORDERLINE_RISK с баллом 30–59. Остальные маршруты запрещены для одобрения.
- Сохранённые результаты ФНС/БКИ и снимок продукта используются повторно без новых обращений к симуляторам. Изменение текущего каталога или профиля не меняет основание предложения.

## 4. Swagger и API

В Swagger http://localhost:8000/docs войти сотрудником: GET `/api/auth/csrf`, POST `/api/auth/login` с X-CSRF-Token, затем получить новый токен сессии. Все POST требуют cookie, текущий X-CSRF-Token и допустимый Origin.

POST `/api/bank/applications/{id}/offer-preview`:

```json
{"expected_version": 5, "amount": "1500000.00", "term_months": 36}
```

Версию 5 заменить актуальной из GET банковской карточки. Ответ: application_version, terms (исходные и предложенные условия, pricing, нагрузка), risk_score/risk_band, routing, reasons, can_approve и preview_hash. Расчёт не меняет версию заявки и не создаёт Assessment/Decision/события.

POST `/api/bank/applications/{id}/decision`:

```json
{
  "expected_version": 5,
  "outcome": "APPROVED",
  "public_explanation": "Предлагаем меньшую сумму и увеличенный срок для снижения нагрузки.",
  "internal_comment": null,
  "offer": {
    "amount": "1500000.00",
    "term_months": 36,
    "preview_hash": "вставить 64 символа preview_hash из своего расчёта"
  }
}
```

`offer` необязателен: без него прежнее одобрение/отказ работают как раньше. Для REJECTED offer запрещён (422). Подмена просмотренных параметров/хеша — 409 OFFER_PREVIEW_CHANGED; старая version — 409 VERSION_CONFLICT; запрещённый расчёт — 422 OFFER_NOT_APPROVABLE; неверные границы — 422 OFFER_AMOUNT_INVALID/OFFER_TERM_INVALID; те же условия — 422 OFFER_UNCHANGED. CLIENT получает 403, без сессии — 401, без CSRF — 403.

После успеха публичный Decision.offer содержит только сравнение условий и pricing, без риск-балла и внутреннего контекста. Банк дополнительно получает offer_risk_score/offer_risk_band. В банковских списках approved_amount/approved_term_months и terms_changed отделены от исходных requested_amount/term_months. OpenAPI и TypeScript обновлены.

## 5. Данные, история и ИИ

`decisions.offer_snapshot` хранит BANK-OFFER-1, исходную отправку/hash и assessment_id, версию заявки при расчёте, исходные/новые условия, полный расчёт, риск, причины и preview_hash. Эти сведения записываются вместе с единственным финальным решением, сотрудником, временем и событием DECISION_MADE с terms_changed=true. Исходные ApplicationRevision/Assessment/CheckResult не заменяются; нового assessment run нет. Цель и подтверждения остаются из отправки. У прежних решений offer_snapshot=null.

GET agreement и демо-подпись используют финальные поля Decision. Подписанный документ сохраняется в applications.signing_record по прежней схеме. База хранит отдельно первоначальный запрос, основание проверки, предложение банка и принятый клиентом документ.

После одобрения POST advisor объясняет сохранённое одобренное предложение; в его scenarios один REQUESTED с итоговыми суммой/сроком/ставкой/платежом, без нового торга альтернативами. Предыдущие отчёты остаются историей и получают is_current=false после смены решения/статуса. Возможности модели и веса не меняются. Новую генерацию по финальному решению можно проверить через Swagger; клиентский глобальный помощник читает последний сохранённый разбор.

PostgreSQL: одно решение при гонке, JSONB/модели без расхождений, сохранность после перезапуска. React: расчёт, запрещённая нагрузка, одобрение, сравнение у клиента, подпись и перезагрузка списка.
